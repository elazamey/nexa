هذه شريحة تكامل فعلية ذات نقطة دخول محلية واحدة، وليست إعلان اكتمال التقنيات الـ200. تجمع المكوّنات الآمنة المتاحة، وتكشف غير الموصول منها. **لا تشغيل أوامر، لا تطبيق patch، لا WRITE/COMMIT/create، لا تفعيل نموذج، لا Supabase أو نشر.** لم تُعدّل منافذ التنفيذ القديمة أو اختبارات RED لإخفاء إخفاقاتها.

## 1. التشغيل

من جذر المستودع:

```bash
node tools/celia-system.mjs --help
node tools/celia-system.mjs status
node tools/celia-system.mjs catalog
node tools/celia-system.mjs status --state /home/user/nexa-learning-data
node tools/celia-system.mjs fingerprint --input /absolute/path/plan.json
node tools/celia-system.mjs advise --input /absolute/path/request.json
```

يوجد اختصار `npm run --silent celia:system -- <command>`. استخدم `--silent` أو `node` مباشرةً إذا أردت JSON فقط. النتائج على stdout؛ لا يكتب البرنامج ملفات تقارير. حفظ stdout، إن اخترته، فعل صريح من المشغّل وليس صلاحية حصلت عليها توصية.

- `advise --state <directory>`: يقرأ مجموعة موجودة ومراجَعة فقط؛ لا ينشئها ولا يضيف نتائج إليها.
- `advise --model <candidate.json>`: يستخدم مرشحًا يقدّمه المشغّل صراحةً؛ لا يبحث عن نموذج افتراضي، ولا يتصل بـLLM، ولا يستبدل المفقود بمحاكاة.
- `verify --input <report.json> --expect-reporter <trusted-key-id>`: يتحقق من سلامة التقرير والسلاسل مع هوية متوقعة مستقلة.
- `train --state <directory> --family ml` أو `dl`: تدريب حسابي محلي صريح عبر المتعلّم السابق، والمرشح إلى stdout فقط. مجموعة فارغة أو غير كافية تعطي خطأ، لا نموذجًا وهميًا. ليست هذه عملية تفعيل أو تعلّم تلقائي.
- `research --query "software repair"`: طلب شبكة صريح، للقراءة فقط من arXiv عبر الموصل السابق. لا PDF أو تنفيذ أو إدخال تلقائي في التدريب. فشل الشبكة يُعاد خطأ؛ لا نتائج بديلة مختلقة. وجود الأمر لا يثبت الاتصال الحي؛ لم تُعد محاولة المصدر الحي في هذه الحزمة، والمحاولة السابقة فشلت.

لا توجد أوامر `init/plan/result/review/execute/commit/promote` في هذه الواجهة. جمع البيانات ومراجعتها يظلان إجراءً منفصلًا، موثقًا في [دليل التعلّم](celia-adaptive-learning.ar.md)، ولا يُستدعيان خفيةً أثناء النصيحة.

## 2. ما تم توصيله فعلًا؟

```text
JSON محدود + هدف + خطط قدّمها المشغّل + تقارير TAP اختيارية
  → عقد صارم وربط المهمة/base/suite/عدد الاختبارات
  → برنامج Ω ثابت يملكه المضيف؛ لا إدخال نص المستخدم في DSL
  → Compiler → Authority → Capabilities → Policy → Kernel
      1. قراءة بصمة الطلب من سياق محلي، لا من مستودع حي
      2. فهرسة الخطط المقدّمة، لا توليد إصلاحات
      3. فحص ملخصات TAP ومخاطر الخصائص المصرّح بها
      4. ترتيب تجريبي بنموذج صريح، أو الامتناع عند غيابه
      5. حفظ بصمة النتيجة في working memory داخل العملية
  → ملاحظة التشغيل المحلي + Reflection
  → ملخص نقدي + حالة التعلّم + سلاسل أدلة + ختم التقرير
```

الصلاحيات الداخلية قصيرة العمر ومحددة **للحسابات المحلية وذاكرة العملية فقط**. ينشئ المضيف المحلي هويات مؤقتة جديدة في كل تشغيل؛ هذه ليست هوية مستخدم HTTP أو صلاحيات على workspace. لا يُعرَض كائن session أو kernel أو مفاتيح التوقيع عبر الواجهة.

تُستخدم نواة NEXA الفعلية وإيصالاتها، لا `coder/tester` ذوي النتائج الثابتة في الأمثلة، ولا telemetry عشوائية من infinite kernel. يوجد فعلًا خمس مكالمات محلية مؤمّنة في المسار الناجح. **نجاحها يعني اكتمال التحليل، وليس نجاح الاختبارات المستوردة أو صحة الإصلاح.**

مخرجات Reflection مشتقة من هذه المكالمات الحقيقية فقط. لا نختلق TOOL_RESULT لتشغيل patch لم يحدث. قد تكون نافذة الانعكاس بلا إخفاقات رغم فشل اختبارات مرشّح، لأن قارئ التقرير نفسه نجح؛ الفشل الدلالي ظاهر في `assessments`. لا قياسات تكلفة/زمن/رموز مزعومة؛ حقول الملاحظة غير المقاسة تحمل `measured: false`.

## 3. عقد الطلب

الحقول الجذرية **بالضبط**: `version`, `operation`, `goal`, `plans`, `reports`.

- `version: 1`, `operation: "advise"` فقط.
- `goal`: الحقول `id`, `description`, `taskGroup`, `baseHash`, `suiteHash`, `expectedTests` فقط. وصف غير فارغ حتى 4000 محرف.
- `plans`: من 1 إلى 32 خطة، بعقد المتعلّم السابق الموضح أدناه. المعرّفات فريدة؛ كل خطة تطابق هدفها في المهمة وbase وsuite وعدد الاختبارات.
- `reports`: صفر أو تقرير واحد لكل خطة. الغياب مسموح ويعني `UNVERIFIED`، لا PASS.
- كل تقرير يحوي `planId`, `planHash`, `tap`, `exitCode` فقط. `planHash` ناتج أمر `fingerprint` للخطة كاملة، و`tap` نص تقرير Node مكتمل، لا مسار ملف يُنفذ.

هيكل توضيحي **غير صالح للتشغيل قبل استبدال placeholders ببياناتك الفعلية**:

```json
{
  "version": 1,
  "operation": "advise",
  "goal": {
    "id": "review-issue-1",
    "description": "فحص خطط الإصلاح المقدمة دون تنفيذها",
    "taskGroup": "repo:issue-1",
    "baseHash": "<64 lowercase hexadecimal characters>",
    "suiteHash": "<64 lowercase hexadecimal characters>",
    "expectedTests": 2
  },
  "plans": [{
    "id": "attempt-1",
    "taskGroup": "repo:issue-1",
    "strategy": "minimal-fix",
    "features": {
      "changedFiles": 1,
      "changedLines": 10,
      "dependencyChanges": 0,
      "baselineFailures": 1,
      "testFilesChanged": 0,
      "touchesSecurityBoundary": 0
    },
    "baseHash": "<same baseHash as goal>",
    "patchHash": "<64 lowercase hexadecimal characters>",
    "suiteHash": "<same suiteHash as goal>",
    "expectedTests": 2,
    "researchIds": []
  }],
  "reports": []
}
```

الأعداد في المثال شرح للبنية، لا قياس لمستودع المستخدم. لتضمين تقرير فعلي أضف:

```json
{
  "planId": "attempt-1",
  "planHash": "<fingerprint command result>",
  "tap": "<complete TAP text from your separately executed test run>",
  "exitCode": 0
}
```

استخدم exitCode الفعلي، لا صفرًا افتراضيًا. تغير أي جزء من الخطة يغير ربط التقرير. `planFingerprint` هو SHA-256 على تمثيل NEXA canonical للكائن `{domain: "celia-advisory-plan-v1", plan}`؛ **ليس** بصمة JSON غير المرتب الخاصة بالجامع القديم. كذلك بصمات الطلب/الوصف/نص التقرير في هذه الشريحة canonical؛ لا تخلطها ببصمات الملفات الخام أو Git SHA-1. بصمة النموذج تبقى بعقد المتعلّم السابق.

يرفض النظام الحقول الإضافية، العملية غير الاستشارية، الخصائص غير المحدودة، الربط المختلف، التقارير المكررة أو غير المكتملة، ومخرجات النماذج غير الصالحة. حد الطلب 2 MiB، ونص TAP الواحد 1 MiB، والنموذج 256 KiB، والتحقق من التقرير 4 MiB. القراءة المحلية محدودة للملفات العادية، مع رفض الرابط الرمزي النهائي والملفات متعددة الروابط؛ **ليست عزلًا شاملًا لمسارات جهاز المشغّل أو حماية من كل سباقات الملفات**.

## 4. قراءة النتيجة دون تحويلها إلى تصريح

| الحقل/الحالة | المعنى المحدود |
| --- | --- |
| `workflow.status: COMPLETED_LOCAL_ANALYSIS_ONLY` | برنامج التحليل الثابت انتهى؛ لا حكم على تطبيق الإصلاح |
| `REPORTED_CHECKS_MET` | الملخص المقدّم متسق، وعدده متوقع، وكل اختبار ناجح، وexitCode صفر |
| `REPORTED_CHECKS_NOT_MET` | فشل/إلغاء/skip/todo أو اختلاف العدد أو exitCode غير صفري |
| `UNVERIFIED` | لا تقرير للخطة؛ لم يُنفّذ اختبار بديل |
| `humanReview: NOT_RECORDED_BY_THIS_SYSTEM` | لا موافقة بشرية تلقائية على المرشّح الحالي |
| `NO_MODEL` / `UNSEEN_STRATEGY` | لا درجة؛ الامتناع أفضل من اختلاق تقييم |
| `scoreBasisPoints` | تقريب الدرجة التجريبية ×10000 لتوقيع أعداد صحيحة؛ ليست احتمالًا معايرًا ولا ثقة أمنية |
| `executionAllowed: false` | ثابت في النتيجة والتوصيات؛ لا تقدم التوصية أي صلاحية |

المخاطر مستنتجة من **خصائص يصرّح بها المشغّل**، وليست تحليلًا لمحتوى patch: تعديل اختبارات أو اعتماديات أو حد أمني يولّد ضرورة مراجعة مستقلة. لا يخفي ارتفاع درجة النموذج إخفاق تقرير الاختبار، ولا يعني ترتيبه أولًا أنه الخيار المقبول.

تقارير TAP والـhashes وخصائص الخطط مصادر مستوردة غير موثَّقة تنفيذيًا: يمكن لمقدّمها الكذب. هذه الواجهة لا تقرأ المستودع للتحقق من base/patch/suite، ولا تشهد بأن الاختبارات شُغلت أصلًا أو على تلك البايتات. لا تُحوَّل النتيجة إلى `makeObservation` أو مكافأة أو مراجعة بشرية تلقائيًا.

## 5. الأدلة والتعلّم والذاكرة

- التقرير يتضمن سلسلة Ω، وسلسلة قرارات النواة، وختم Ed25519 يربط **التقرير كاملًا** ببصمته. البتر والتعديل والإلحاق يفسدان التحقق.
- `verify` يطلب `expectedReporter` مستقلًا. سجّل هوية `reporter` عند الإنشاء من عملية موثوقة أو قناة مستقلة؛ استخراج الهوية من الملف غير الموثوق نفسه ثم تمريرها لا يثبت مصدره. المفاتيح جديدة لكل تشغيل، ولا توجد هوية خدمة ثابتة أو ثقة تلقائية بالموقّع.
- التوقيع يثبت سلامة المحتوى بالنسبة للمفتاح المتوقع؛ **ليس تصريح تنفيذ، ولا إثبات صدق TAP، ولا attestation خارجية أو حماية من إعادة عرض تقرير قديم**. قارن `requestHash` بطلبك المتوقع واحتفظ بسياسة حداثة مستقلة إذا احتجتها.
- النص الخام للهدف وTAP ومصفوفات أوزان النموذج والمفاتيح الخاصة لا تُنسخ إلى التقرير. لكنه يحتوي معرّفات الخطط والمجموعات وبصمات وبيانات وصفية؛ لا تعتبره خاليًا من المعلومات الحساسة أو آمنًا للنشر العام تلقائيًا.
- working memory مؤقتة، تحفظ بصمة فقط، وتبدأ فارغة كل مرة. لا checkpoint، استرجاع بين العمليات أو مخزن أدلة دائم في هذه الشريحة.
- بدون `--state`: `NOT_CONNECTED` وعدد عينات غير معلوم، لا ادعاء فحص مجموعة. مع المجموعة الفارغة: `COLLECTING`, `samples: 0`, `trained: false`.
- وجود نموذج صريح لا يجعل مجموعة البيانات مدرّبة تلقائيًا؛ حالة المجموعة منفصلة عن `ranking.model`. وزن صالح وبصمته لا يثبتان مصدر التدريب أو جودة الإصلاح. درجة المرشح غير معايرة ويظل غير مفعّل.
- بوابات حجم/توزيع مجموعة التدريب وشروط الفصل والمراجعة السابقة لم تتغير. مراجعات المجموعة لا تُستنسخ موافقات على خطط هذا الطلب. التحسن على fixtures العددية الاصطناعية لا يثبت تحسن إصلاحات المستخدم.

## 6. كتالوج الـ200 بند

`catalog` يعرض A001–A100 وB001–B100 بالأسماء والترتيب الأصليين. المصدر [مصفوفة التدقيق](nexa-capability-matrix.ar.md)، ونسخة البيانات في `system/src/catalog-data.js`، واختبار يطابقها مع CSV.

**محوران مستقلان:**

1. `auditStatus`: التصنيف السابق M16 / P116 / D16 / N52؛ لا يتغير إلى «مكتمل» بمجرد تسجيل الاسم.
2. `integration`: **25 CONNECTED_LIMITED، 3 CONDITIONAL_LOCAL_DATA، 8 BLOCKED، 164 NOT_CONNECTED** في هذه الشريحة.

الـ25 روابط محدودة إلى خدمات فعلية مسماة في `service`، وليست 25 تقنية منفذة بكامل تعريفها، وليست وحدات مستقلة أو نسبة اكتمال. مثلًا الذاكرة بصمات مؤقتة، والتخطيط سير فحص ثابت، والنقد قواعد محدودة. البنود الشرطية تعتمد على وجود تقارير أو نموذج أو بيانات مراجَعة. البنود غير الموصولة لا تستدعي محاكاة بديلة. عرض Chain of Thought في الكتالوج لا يعني إظهار استدلال داخلي؛ هو غير موصول، والسير المعلن مجرد خطوات عمل عامة.

## 7. أدلة قبول هذه الحزمة وحدودها

الفحوص المنفذة محليًا بتاريخ هذه الوثيقة:

| الفحص | النتيجة |
| --- | --- |
| `tests/celia-system.test.js` + `tests/celia-learning.test.js` | **39/39**، منها 21 جديدة للتكامل |
| persistence + commit-auth + commit-http + workspace-http + write-auth | **59/59** |
| `npm run verify` | **415 اختبارًا: 413 PASS / 2 FAIL**، exit 1 |
| posture ضمن verify | **6 gates CLOSED** |
| الاختبارات السابقة والشفرة الموجودة قبل التكامل | مطابقة بصمات 295 ملف JS/MJS سابقًا، لا تغييرات فيها |

الاختبارات الجديدة تشغّل فعليًا fixtures Node ناجحة وفاشلة ثم تمرر TAP إلى CLI، وتتحقق من الرفض والربط والتلاعب بالأدلة. تُشغَّل الواجهة أيضًا تحت Node Permission مع قراءة فقط، دون منح كتابة أو child processes، وتُقارن محتويات وtopology وmetadata دليل الاختبار قبلها وبعدها (باستثناء atime الذي قد يتغير بالقراءة). التدريب العددي في الاختبارات **اصطناعي معلن** ولم يدخل المجموعة الحقيقية.

في المحاولة الأولى لاختبارات التكامل ظهر رفض `REPORT_PREDATES_REGISTERED_PLAN` في fixture جديد بسبب توقيت كتابة الملف؛ أُعيد بناء ذلك fixture ليولّد التقرير من تشغيل Node فعلي بعد التسجيل، دون تغيير عقد الجامع أو اختبار سابق. آخر الجولة المستهدفة والشاملة موثقتان أعلاه.

الفشلان الشاملان، دون تعديل اختباراتهما:

- **H2:** فشل كتابة الملف الثاني يترك الأول مطبّقًا جزئيًا.
- **H3:** كاتب خارجي بعد التحقق يُطمَس ببايتات COMMIT القديمة.

H1 اجتاز فحص إعادة التشغيل الحالي. **لا تعني هذه الحزمة إصلاح H2/H3**. مراحل audit/demo/attacks/report التالية في سلسلة `verify` لم تُنفذ لأن `npm test` أعاد الفشل. المجموعة الحقيقية `/home/user/nexa-learning-data` فُحصت وبقيت صفر خطط/عينات/مراجعات، دون نموذج مفعّل.

لإعادة الفحص:

```bash
node --test tests/celia-system.test.js tests/celia-learning.test.js
node --test tests/celia-workspace-commit-persistence.test.js tests/celia-workspace-commit-auth.test.js tests/celia-workspace-commit-http.test.js tests/celia-workspace-http.test.js tests/celia-workspace-write-auth.test.js
npm run verify
```

ملخص القياس: الشريحة الاستشارية **اجتازت الفحوص الحالية الخاصة بها**، أما النظام الكامل فليس GREEN أو جاهزًا للإنتاج. لا HTTP جديد، لا خدمة عامة، لا UI جديدة، ولا استدعاء لمسارات workspace أو create أو Supabase. لم يحدث merge أو deploy.

## 8. التراجع والخطوة التالية

التكامل إضافي: التراجع يكون بإزالة مجلد `packages/cells/celia/system`، وأداة `tools/celia-system.mjs`، واختبارها الجديد واختصار npm وروابط الوثائق؛ لم ينفذ أي migration أو تغيير في صيغة مجموعات المستخدم أو النواة أو منافذ COMMIT. لا تحذف الأدلة أو البيانات الخارجية ضمن التراجع.

قبل أي توسعة تنفيذية: حزمة H2 مستقلة RED→إصلاح أدنى→نفس الاختبار GREEN→انحدار؛ ثم H3 بالطريقة نفسها، ثم جميع اختبارات الحدود والفحص الشامل، ثم تقييم crash consistency وتزامن عدة commits. create وSupabase والنشر لها بوابات مستقلة، ولا تفتحها هذه الواجهة أو درجة نموذج.
