## 2. الإصلاح المحدود

[مخزن الاستهلاك](../tools/celia-commit-consumption-store.mjs) مستقل عن الجذر المستهدف وعن قاعدة بيانات المنح:

- إعداد موثوق مستقل: `CELIA_COMMIT_STATE_DIR`، أو معامل `stateDirectory` عند بناء المنفذ. لا fallback إلى الذاكرة أو مجلد مؤقت، ولا إنشاء/reset تلقائي عند الطلب.
- دليل دائم خارج root، مملوك لمستخدم الخدمة، بصلاحيات خاصة `0700` وملفات `0600`. ترفض الروابط الرمزية والملفات غير العادية/hard links والمسارات غير المناسبة. الدليل وأسلافه والتخزين ضمن حدود الثقة التشغيلية.
- `store.json`: هوية المخزن وربطه بـtargetRoot. `journal.jsonl`: رأس ثم سجلات **CONSUMED** متسلسلة ومترابطة بالبصمات. `head.json`: عدد السجلات وبصمة آخر سجل؛ يكشف قص نهاية journal حتى إذا حُذفت سجلات كاملة وظل JSON صالحًا.
- يسجل الاستهلاك: request ID وnonce، subject وaudience، authorizationRef، scope الكامل، ومعرفات **جميع حلقات capability chain** وميزانياتها. لا يحفظ مفاتيح خاصة أو محتوى الملفات.
- قفل `reservation.lock` بـexclusive-create، ثم قراءة سجل القرص وإعادة بناء الاستخدامات تحت القفل؛ لا تُعامل cache العملية كمرجع بعد restart.
- عند الحجز: append للسجل ثم `fsync(journal)`، تحديث رأس السجل و`fsync(head)`، ثم إغلاق/إزالة القفل و`fsync(directory)`، **وكل ذلك قبل mkdir/write للجذر**.
- الـReplayGuard وUsageLedger الموجودان يظلان cache داخل العملية. الاستهلاك الدائم مطلوب قبل تحديثهما وتنفيذ الأثر. لا يسمح authorizer باستهلاك ذاكرة فقط عند غياب موفر الاستهلاك الدائم.
- إعادة استخدام request/nonce أو منحة مستهلكة أو budget سلف مستنفد: **403**. تعذر/فساد المخزن: **503** دون كتابة للجذر. أخطاء الكتابة أو fsync غير المحسومة تُبقي القفل؛ restart لا يمسحه تلقائيًا.
- لا يعيد فشل التطبيق المنحة المستهلكة إلى الحالة المتاحة. الحالة تعني **حجز/استهلاك الإذن قبل محاولة التنفيذ**، وليست إيصال نجاح المعاملة.

التعديلات الإنتاجية مقتصرة على المخزن الجديد وربطه في authorizer وcommitter. لم يُغيّر مسار التطبيق المتتابع لإصلاح H2 أو H3، ولا وحدات البروتوكول الأساسية أو WRITE أو إعداد policy الخاص به.

## 3. أدلة إضافية: 20/20

[اختبارات persistence الجديدة](../tests/celia-workspace-commit-persistence.test.js) تنفذ الشفرة الإنتاجية الفعلية في عمليات منفصلة وملفات مؤقتة معزولة:

1. قراءة سجل CONSUMED من القرص ومطابقته للتفويض والنطاق، ثم ABA وrestart ورفض الطلب القديم **403** دون تغيير جذر المشروع أو metadata المقاسة.
2. طلب موقع حديث بـID وnonce جديدين لكن **المنحة القديمة المستهلكة**: **403**؛ يمنع إصلاحًا سطحيًا يحفظ envelope IDs فقط.
3. **منحة جديدة صحيحة لنفس workspace/root/changeSet/base بالضبط: ALLOW**، مع تطبيق A+B فعليًا وسجل استهلاك ثانٍ. لا حظر دائم للـchangeSet.
4. **SIGKILL** عند أول root write، بعد انتهاء الحجز الدائم وقبل الأثر: جذر المشروع لم يتغير، يوجد سجل الاستهلاك ولا يوجد قفل متروك. بعد restart: القديم **403 من السجل نفسه**، وليس 503 بسبب قفل؛ الجديد **ALLOW**. هذا يثبت ترتيب الاستهلاك قبل الأثر في نقطة الفشل المقاسة.
5. سلف بميزانية 2 وثلاث منح أبناء صحيحة: الابن الأول **ALLOW**، وبعد restart الثاني **ALLOW**، وبعد restart الثالث **403** بسبب ميزانية السلف المستهلكة. التواقيع والزمن والنطاق لا تزال صحيحة.
6. حقن ENOSPC عند كتابة journal، وEIO عند fsync للـjournal وللـhead: **503** دون أي root write؛ restart يبقى fail-closed على القفل غير المحسوم، حتى لمنحة جديدة.
7. فقد التهيئة، فقد journal، سجل مبتور، حذف سجل كامل، head فاسد، دليل غير خاص، journal غير قابل للقراءة/الكتابة، symlink، وربط root مختلف: لا يُفسر أي منها كسجل جديد فارغ. لا كتابة للجذر.
8. أول طلب صحيح مع مخزن لم يُهيّأ، أو غياب إعداد الدليل: **503** ولا fallback. initializer يرفض reset لمخزن مستخدم، والطلب المجهول **401** لا يعدل المخزن أو الجذر.

إثبات restart هنا عند حد COMMIT المباشر، **وليس اختبار HTTP recovery**. fixture يعيد تسجيل locator للـworkspace كما في اختبار H1 الأصلي، دون استعادة ذاكرة replay/usage. الـ39 السابقة أدلة HTTP مستقلة. إضافات fault bootstrap تعمل على IO الحقيقي؛ لا تستبدل verify/hash/policy أو قرار ALLOW/DENY.

امتد fixture المشترك فقط لتهيئة مخزن منفصل وإعادة استعماله عبر restart وتنظيفه بعد الاختبار، مع API إضافية لمنح جديدة. تهيئة اختبارات HTTP المصرح لها أصبحت تضبط المخزن الخارجي أيضًا. **ملفات اختبارات القبول السابقة والـhardening worker الأصلي وHTTP child بقيت byte-for-byte كما هي.** لا ندّعي أن ملفات helper لم تتغير.

## 5. تهيئة التشغيل — عقد إضافي، وليس إذن نشر

هذا الجزء توثيق للمشغّل فقط؛ **لم تُهيّأ خدمة فعلية أو مخزن production في هذه الجولة**.

1. يجهز المشغّل دليلًا دائمًا فارغًا خارج جذر المشروع، مملوكًا لمستخدم الخدمة بصلاحية `0700`؛ ليس تحت `/tmp` أو staging أو مسار rollback للمشروع. الاختبارات وحدها تستخدم tmpdir وتزيله.
2. من وحدة موثوقة وبحساب الخدمة، تُستدعى مرة واحدة:

```js
import { initializeCommitConsumptionStore } from './tools/celia-commit-consumption-store.mjs';
import { workspaceCommitRoot } from './tools/celia-workspace-commit-port.mjs';

initializeCommitConsumptionStore({
  directory: trustedPersistentDirectory, // دليل فارغ موجود مسبقًا
  root: absoluteRepositoryRoot,
  targetRoot: workspaceCommitRoot(absoluteRepositoryRoot),
});
```

3. يضبط `CELIA_COMMIT_STATE_DIR` على الدليل نفسه في كل restart، مع إعداد `CELIA_WORKSPACE_COMMIT_AUTH` المعتاد. الضمان يتطلب الاحتفاظ **بالمخزن نفسه**؛ لا تبديله بمخزن فارغ ولا استخدام مخزن مستقل لكل worker.
4. حد السعة الحالي: 10,000 سجل و16 MiB للـjournal؛ بلوغ الحد يفشل مغلقًا. لا توجد compaction أو garbage collection أو ترقية/recovery تلقائية في هذه الحزمة.
5. حالة lock متروك أو mismatch أو IO غير محسوم تعني إيقاف COMMIT للتحقيق. **لا توجد هنا وصفة معتمدة لمسح القفل أو إعادة تهيئة المخزن أو استعادة نسخة أقدم**؛ هذا قد يحيي تفويضات مستهلكة. يلزم بروتوكول recovery مدقق قبل توفير تلك العمليات.

عقد التخزين الحالي: filesystem محلي POSIX يدعم exclusive-create وfsync للملفات والأدلة، ويحترم تأكيدات المتانة. ليس دعمًا مثبتًا لـNFS أو أنظمة موزعة أو كل منصات Node. hash-chain وhead يكشفان أخطاء الاتساق المقاسة، لكنهما ليسا توقيعًا مستقلًا أو حماية من مسؤول/عملية تملك حق إعادة كتابة المخزن كاملًا أو rollback متناسق للـjournal والـhead. استعادة القرص/VM أو فقده خارج ضمان restart الحالي.

## 6. الحدود والتراجع والقبول التالي

- H1 **اجتازت الفحوص الحالية ضمن عقد التخزين المذكور**؛ لا تعني crash consistency شاملة. SIGKILL عند نقطة واحدة وحقن IO ليستا اختبار انقطاع كهرباء أو كل crash points.
- H2-ATOMICITY وH3-CONCURRENCY حزمتان لاحقتان مستقلتان، باختبارات RED الأصلية دون تغيير توقعاتها.
- بعدهما يلزم **H1+H2+H3 PASS، و39 PASS، وfull verify PASS**، ثم تقييم crash consistency وعمليات COMMIT المتعددة المتزامنة قبل أي وصف بالجاهزية الإنتاجية.
- للتراجع الآمن: إزالة إعداد تمكين COMMIT وإعادة التشغيل لتعطيله، مع حفظ مخزن الاستهلاك. لا إعادة المسار القديم غير المحمي أو الرجوع إلى replay الذاكرة؛ التعطيل لا يلغي تغييرات ملفات سابقة.
- create وSupabase وRLS والموصل الفعلي والنشر والدمج لم تتغير؛ لا توسع نطاق أو migration حية.
