# خطة استكمال Celia/NEXA — حزم جاهزة للبدء المنضبط

**التاريخ:** 20 سبتمبر 2026. **نوع التسليم:** خطة تنفيذ، وليست تنفيذًا أو تفويض نشر.

## 1. القرار والهدف

نستكمل الموجود بدل بناء نظام موازٍ: **إغلاق حدود الملفات → هوية وعزل وصلاحيات → تشغيل دائم وموصلات → إصلاح محدود مقاس → واجهة → تعلّم وتحسينات اختيارية**.

ثلاثة مستويات يجب عدم خلطها:

1. **الموجود الآن:** نظام استشاري موحّد؛ لا ينفذ أوامر أو patches أو COMMIT.
2. **المنتج الأول المستهدف:** دورة إصلاح محلية محدودة، قابلة للمراجعة والاستعادة، بتطبيق مصرح به على نطاق محدد. ليس تشغيلًا عامًا ذاتيًا أو ضمان خلو من الأخطاء.
3. **تغطية الـ200 تقنية:** لكل بند حزمة ومسار قبول في المصفوفة المرفقة. بعض التقنيات تحتاج نموذجًا/عتادًا/بيانات أو بحثًا مستقلًا؛ قرار تأجيل أو NO_GO لا يعني أنها نُفذت. اكتمال المنتج المحدود ليس اكتمال الـ200.

**التسليمات القابلة للاستخدام مباشرةً:**

- [Backlog من 19 حزمة بصيغة CSV](nexa-execution-backlog.csv): المالك الوظيفي، التبعيات، الحالة، الملفات، القبول والتراجع.
- [خريطة تنفيذ لكل البنود الـ200](nexa-execution-map.csv): تحتفظ بالأسماء والترتيب والفجوات والقبول السابق، وتضيف حالة الاتصال الحالية والحزمة المسؤولة.
- [دليل النظام الحالي](celia-system.ar.md)، و[الخطة المعمارية الأصلية](nexa-capability-expansion-plan.ar.md).

الـCSV جاهز للاستيراد إلى لوحة مهام، لكن **لم تُنشأ GitHub issues**. المالك الوظيفي ليس شخصًا عُيّن أو وافق. `planning_state` حالة انتظار وتبعيات، لا موافقة تنفيذ. `primary_package` ملكية أساسية للتتبع، لا حصر لجميع التبعيات؛ ضوابط الهوية والذاكرة والتقييم مشتركة بين البنود.

هذه نتائج الحزمة السابقة، **لم يُعد تشغيل الاختبارات في جولة التخطيط هذه**. أول إجراء في P00 يعيد قياسها. الخطة الأصلية ذات 394 اختبارًا سجل تاريخي، لا مرجع عددي حالي. لا reset أو تنظيف يمحو ملفات المستخدم أو الشريحة المحلية السابقة. قبل تغيير الشفرة تُحفظ بصماتها ونقطة استعادتها؛ عند الإذن بتسجيل commits، تُفصل الشريحة الاستشارية عن إصلاح H2 في سجل مستقل.

## 3. ترتيب التنفيذ وبوابات التوقف

```text
P00 baseline → P01 H2 → P02 H3 → P03 recovery/concurrent commits
  → P04 identity/approval/contracts → P05 isolated runner
      ├─ P07 create/mutation contracts
      ├─ P06 durable workflow/memory/evidence → P10 provider/context
      │     └─ P08 DB ownership/RLS → P09 real DB connector [إذا اختير DB]
      └─ P11 evaluation/security corpus
  P06 + P10 + P11 → P12 bounded repair pilot → P13 operator interface
  P03 + P07 + P12 + P13 → P18 limited release review [لا نشر تلقائي]

مسارات لاحقة: P11 + P12 → P14 learning / P16 multi-agent
              P11 → P15 knowledge/formal / P17 specialist spikes
```

- لا عمل تنفيذي على create أو Supabase أو تشغيل عام قبل إغلاق P03، وبوابة كل منهما المستقلة بعد ذلك.
- يمكن تجهيز وثائق العقود والتقييم بالتوازي، لكن **لا يصل مسار مؤثر إلى المستخدم قبل اجتياز تبعياته**.
- لا يلزم Supabase لإكمال pilot محلي إذا استُخدم مخزن محلي معتمد. إدخاله يضيف P08/P09 ولا يلغي اختبارات الملكية والاستمرارية.
- P14/P15/P16/P17 ليست شرطًا لإصدار محدود لا يدّعي قدراتها. تفعيل أي منها يجعل قبولها شرطًا للإصدار نفسه.
- لا تُفتح البوابات الست، ولا يُخفى تنفيذ أمر وراء اسم أداة استشارية. إن احتاج تصميم التشغيل المستهدف تغيير العقد الأمني، يتوقف حتى قرار معماري وموافقة مستقلين؛ لا التفاف على `check-posture`.

## 4. بطاقات الحزم

المسارات أدناه أهداف مراجعة/تعديل لاحقة، لا ملفات عُدّلت الآن. أي اختبار جديد يضاف في ملف مستقل؛ **الاختبارات السابقة وfixtures الخاصة بها لا تُغيّر لإنتاج GREEN**.

<a id="p00"></a>
### P00 — تثبيت baseline — أول حزمة قابلة للبدء بعد الإذن

**المالك:** QA + Security. **التبعيات:** لا شيء.

- جرد جميع التغييرات المحلية، وتثبيت SHA-256 لاختبارات الحدود والشفرة والإعدادات، وحفظ إصدار Node/npm والأوامر وexit codes خارج بيانات المستخدم.
- إعادة 39 و59 ثم `verify`؛ توثيق H1 وH2 وH3 كلًا على حدة. العدد 415 حد مرجعي لهذه اللقطة، لا قيمة يُجبر بها test runner على النجاح.
- **القبول:** baseline قابل للإعادة؛ كل فشل جديد مفهوم قبل الإصلاح. **التراجع:** لا تغيير وظيفي؛ لا حذف ملفات محلية أو مجموعات خارجية.

<a id="p01"></a>
### P01 — H2-ATOMICITY — حزمة إصلاح مستقلة

**المالك:** Systems + Security. **التبعية:** P00. **المسار:** `tools/celia-workspace-commit-port.mjs`، واختبارات H2 الجديدة عند الحاجة.

1. إعادة RED الأصلي وتوثيق `write-applied(a.txt)` ثم `fault(b.txt, ENOSPC)`.
2. أصغر إصلاح مقترح: التقاط preimages وخريطة الملفات/الأدلة المنشأة بعد التفويض والتحقق؛ تطبيق محكوم؛ عند خطأ تطبيق، استعادة الآثار المملوكة لهذه العملية فقط وإزالة أدلتها الفارغة فقط. لا `rm -rf` لاستعادة عمياء، ولا تغيير staging.
3. لا يوضع سجل استعادة جديد داخل root أو staging إذا أفسد عقد ثبات topology. لا يُمسح سجل استهلاك التفويض عند الفشل. إن فشلت الاستعادة نفسها: quarantine وحظر الكتابة، لا ادعاء نجاح أو محاولة غير محدودة.
4. إضافة اختبارات فشل عند كل موضع كتابة، وملفات جديدة وأدلة جديدة، وخطأ استعادة؛ دون تعديل H2 الأصلي.

**القبول:** نفس H2 GREEN، والخطأ الأصلي ENOSPC ظاهر، والمحتوى وtopology يعودان كما كانا، وstaging ببايتاته وmetadata لا يتغير. الاختبار الأصلي لا يطالب باستعادة ctime لملف root بعد كتابة/تراجع؛ لا نقدم وعدًا مستحيلًا. H1 و59 و39 بلا تراجع.

**حد الضمان:** استعادة بعد خطأ متزامن داخل العملية؛ ليست atomic visibility للقراء أثناء التطبيق، ولا power-loss recovery أو حماية الكاتب الخارجي. يمكن أن يبقى H3 الفشل الوحيد في `verify` مؤقتًا؛ هذا تقدم P01 فقط، وليس جاهزية COMMIT. **التراجع:** تعطيل التطبيق غير المؤكد مع حفظ الأدلة والتفويض المستهلك.

<a id="p02"></a>
### P02 — H3-CONCURRENCY — إثبات تصميم قبل اعتماد إصلاح

**المالك:** Systems + Security. **التبعية:** P01. **المسار:** commit port، مع إبقاء `tests/fixtures/celia-commit-hardening-child.mjs` كما هو.

1. توثيق من يستطيع الكتابة خارج العملية: نفس UID، مستخدم آخر، مدير نظام، filesystem المستهدف. لا نفترض ملكية حصرية غير مفروضة.
2. spike مقيد: مقارنة آلية transaction/compare-and-apply قابلة للفرض في البيئة مع ملكية كتابة قابلة للإنفاذ؛ تحديد نقطة الربط الذرية بين التحقق والتطبيق، وكيف تحفظ تغيير المنافس.
3. **لا تعتبر lock تعاونية أو rehash قبل write أو rename منفرد إصلاحًا كافيًا.** يجب أن يصل الاختبار الأصلي إلى التدخل الخارجي فعلًا؛ حجب hook أو رفض جميع commits ليس GREEN.
4. بناء أدنى إصلاح يطابق العقد، ثم اختبارات أوقات سباق إضافية ونجاح طلب سليم، بعد قبول ADR. إذا احتاج الحل تغيير العقد الأصلي أو صلاحيات/بيئة غير متاحة، تسجّل نتيجة BLOCKED ويطلب قرار منفصل؛ لا يعدّل الاختبار.

**القبول:** H3 الأصلي GREEN: writer من عملية مستقلة تدخل بعد التحقق وقبل كتابة executor؛ النتيجة DENY 403؛ قيمة الكاتب محفوظة، والملف الآخر غير مطبّق، وstaging ثابت. H1/H2 والانحدار ناجحة و`verify` كامل GREEN قبل اعتماد التنفيذ. **التراجع:** COMMIT يبقى معطلًا إن لم يثبت الضمان. لا موعد إصلاح مضمون قبل ADR؛ التحقيق نفسه مهمة قابلة للتنفيذ.

<a id="p03"></a>
### P03 — الاستعادة بعد الانقطاع والتزامن متعدد العمليات

**المالك:** Systems + QA. **التبعية:** P02. **المسارات:** commit port و`tools/celia-commit-consumption-store.mjs`؛ اختبارات عمليات جديدة.

- تحديد crash points قبل/بعد حفظ نية العملية، واستهلاك التفويض، وكل أثر، وتأكيد النهاية. قياس SIGKILL وإعادة تشغيل فعلية؛ حقن أخطاء fsync/rename عند استخدامها.
- اختبار عمليتين على نفس change/base، وعمليات متعارضة وغير متعارضة. التحقق من ملكية القفل، وعدم إحياء consumed grants، وعدم تكرار التطبيق بعد timeout/retry.
- **القبول:** استعادة حالة محددة قابلة للتحقق، لا root مختلط أو replay، ونسخة احتياطية مستعادة فعليًا. حدود SIGKILL ليست شهادة power-loss على كل storage؛ تُوثق بيئة الضمان واختبارات أدنى الطبقات اللازمة.
- **التراجع:** إيقاف الكتابة وعزل العمليات غير المؤكدة؛ لا كسر قفل عالق آليًا لمجرد موت PID. هذا هو شرط الانتقال لأي توسعة مؤثرة.

<a id="p04"></a>
### P04 — هوية وموافقات وعقود كل المنافذ

**المالك:** Security + Backend. **التبعية:** P03. **المسارات:** dashboard server، workspace auth ports، وإعادة استخدام `packages/{identity,policy,capability}` دون تغيير بواباتها.

- جرد endpoint/port/action/resource/principal لكل وظيفة؛ عقد موحد يرفض extra fields ويحد الأحجام ويثبت مصادر الثقة. لا اعتماد `verified:true` من الطلب.
- إقرار `principal → owner_kid/subject → resource/row ownership`، وموافقة تربط الخطة والعملية والمورد وbase/change hashes والانتهاء والاستهلاك. تغيير الخطة يبطل الموافقة.
- **القبول:** نقص الهوية 401 وفق العقود القائمة، ونقص الصلاحية/مخالفة نطاقها 403، وALLOW موجب بتفويض صحيح؛ cross-user/workspace، expiry/replay، wrong action/resource/state، بلا قراءة/كتابة filesystem قبل نجاح التفويض المطلوب.
- **التراجع:** إغلاق المسار الجديد؛ لا استعادة route قديم غير محمي. WRITE ليس COMMIT، وتوقيع التقرير ليس permission.

<a id="p05"></a>
### P05 — Runner معزول وموارد وأسرار

**المالك:** Platform + Security. **التبعية:** P04؛ بيئة اختبار عزل معتمدة.

- منفذ I/O مستقل في `tools/` أو خدمة معتمدة؛ لا process/filesystem داخل packages pure. الاختيار بين runtime معزول/container/OS controls عبر ADR، لا تسمية blacklist «sandbox».
- أول عقد: تشغيل suite محددة على نسخة عمل معزولة، بلا shell حر يختاره النموذج. حدود CPU/RAM/pids/time/output، شبكة مقفلة افتراضيًا، allowlist egress عند الحاجة، وهوية تشغيل منفصلة وأسرار قصيرة العمر.
- **القبول:** محاولات هروب وقراءة/كتابة خارج المساحة وفروع processes وتسريب أسرار وتجاوز موارد تُرفض فعليًا؛ suite مسموحة تعمل، والفشل لا يسقط إلى host execution.
- لا يُركّب runner داخل `tool:advisory-*`؛ يبقى المسار الاستشاري بلا آثار. **التراجع:** فصل runner وصلاحياته. غياب بيئة عزل مناسبة = BLOCKED، لا mock PASS.

<a id="p06"></a>
### P06 — Workflow وذاكرة وأدلة دائمة

**المالك:** Backend + SRE. **التبعية:** P05. **المسارات:** system/runtime/evidence مع ports للمخزن؛ لا إعادة بناء السلاسل الموقعة من الصفر.

- **P06.1:** state machine وevent schema versioned وidempotency key/leases/retries/cancellation؛ يمنع resume تكرار أثر سابق.
- **P06.2:** ذاكرة بملكية ومصدر وثقة وretention/حذف وحدود حجم؛ فصل حمولة المستخدم عن أسرار السلطة ومخزن استهلاك grants. لا ترقيات معرفية تلقائية من محتوى غير موثوق.
- **P06.3:** تصدير أدلة دائم، وهوية موقّع موثوقة وrotation/revocation/freshness وطلب متوقع؛ بصمات لا تثبت صدق مصدر خارجي. مراقبة مقاسة للزمن والتكلفة والأخطاء، لا أصفار توحي بقياس لم يحدث.
- **القبول:** restart/resume وkill worker وعزل A/B وفساد سجل/bتره وbackup/restore؛ ingestion متكرر بلا أثر مكرر. **التراجع:** وقف workers والحفاظ على التاريخ؛ لا restore للسلطة من نسخة تعيد grants مستهلكة.

<a id="p07"></a>
### P07 — create وبقية التعديلات: عقد مستقل

**المالك:** Security + Backend. **التبعيات:** P04/P05؛ موافقة مستقلة على هذه الحزمة.

- مراجعة `tools/celia-workspace-port.mjs` وdashboard routes؛ create وrollback/delete وغيرها إن كانت مكشوفة، مع صلاحيات منفصلة وتحقق path/identity/state.
- **القبول:** create مجهول 401؛ مستخدم معروف بلا grant 403؛ grant صحيح ومحدد ALLOW؛ تطابق ملكية workspace، traversal/symlink/cross-workspace، وعدم أي تغيير عند DENY. نجاح WRITE أو COMMIT لا يحتسب نجاحًا لـcreate.
- **التراجع:** إغلاق route المخالف، لا إعادة النسخة غير المحمية. لا ينفذ الآن بحجة أن خطة الاستكمال ذكرت اسمه.

<a id="p08"></a>
### P08 — ملكية DB وRLS قبل الموصل

**المالك:** Data + Security. **التبعيات:** P04/P06 وبيئة DB تجريبية مصرح بها. **المسارات:** `supabase/` وعقود memory.

- تثبيت owner mapping وحقوق الجداول والسياسات؛ migrations مقترحة تُراجع قبل التطبيق على قاعدة اختبار منفصلة.
- **القبول:** هوية A وهوية B فعليتان، SELECT/INSERT/UPDATE/DELETE، وفشل تغيير owner، واختبار USING وWITH CHECK؛ الطلبات تحت أدوار المستخدمين لا service-role يتجاوز RLS. SQL inspection وحده ليس دليلًا حيًا.
- **التراجع:** فصل البيئة والموصل؛ لا rollback يعيد سياسات متساهلة. لا migration حي أو ادعاء معرفة وضع deployment الحالي.

<a id="p09"></a>
### P09 — موصل Supabase فعلي

**المالك:** Integrations + Data. **التبعية:** P08. **المسارات:** memory loaders وports داخل tools وفق discovery.

- استبدال مسار loader المعطل بموصل حقيقي محدود الصلاحية في البيئة المعتمدة؛ schema/timeouts/retries لا تكرر الآثار وحدود اتصال واضحة.
- **القبول:** round-trip حقيقي، ownership A/B من خلال الموصل، restart وحالات credentials مفقودة/timeout/429/5xx. صحة RLS وصحة الموصل دليلان مستقلان.
- **التراجع:** تعطيل الموصل؛ لا mock fallback ناجح أو فقد صامت. ليس شرطًا للـpilot المحلي إن لم يختر المنتج DB.

<a id="p10"></a>
### P10 — مزود واحد وسياق وتوجيه محدود

**المالك:** Integrations + Agent. **التبعيات:** P05/P06؛ اختيار مزود وحد بيانات وسقف تكلفة معتمد مسبقًا.

- إعادة استخدام `tools/celia-grok-port.mjs` أو adapter يُختار عبر ADR، و`adapters/mcp`، وتوصيل أداة قراءة واحدة أولًا؛ لا ندعي عمل أي مزود لم يختبر حيًا.
- ContextEnvelope بمصادر غير موثوقة وحدود tokens وتصنيف بيانات؛ output schema ومهلة وrate limits وميزانية. caches تربط principal/model/prompt/context/policy version وتبطل عند تغير الحالة، بلا خلط مستخدمين.
- **القبول:** طلب حي مصرح به، قياس latency/cost حقيقي، prompt/tool injection وtimeout/429 ورفض مخطط الرد؛ لا نتائج صناعية عند غياب الخدمة. لا يختار النص المفتاح أو عنوان egress.
- **التراجع:** العودة لاستشارة بلا نموذج وتعطيل الاتصال؛ لا تخفيض أمني أو مزود بديل غير معتمد.

<a id="p11"></a>
### P11 — تقييم مستقل وجودة وأمن توريد

**المالك:** QA + Security. **التبعية:** P05؛ يمكن تجهيز corpus/عقوده دون تشغيل قبلها.

- corpus إصلاحات مرخصة ومجمدة، تقسيم بحسب المهمة/المستودع، baseline بشري أو deterministic، وholdout لا يراه planner؛ حفظ hashes للـbase/patch/suite/artifact وبيئة التنفيذ.
- عتبات قبول الجودة وعدم التراجع والكلفة والمهلة **تثبت قبل التجربة**، مع حجم عينة ومنهج عدم يقين ملائم؛ لا رقم نجاح يُختار بعد مشاهدة النتائج.
- static/dynamic analysis وdependency/SBOM/vulnerability checks وfuzz/property/mutation؛ قياس false accepts والتسرب بين المهام وحالات عدم اليقين. اختبار يولده النموذج لا يستبدل الأصل المحمي.
- **القبول:** إعادة النتائج، كشف فشل حقيقي ورفض تقرير مزور/قديم/لمرشح آخر، وقياس حدود المنهج. **التراجع:** منع اعتماد التجربة غير القابلة للإعادة؛ لا تدريب على holdout أو محو النتائج السلبية.

<a id="p12"></a>
### P12 — وكيل إصلاح محدود النطاق

**المالك:** Agent + QA. **التبعيات:** P06/P10/P11؛ موافقة صريحة على pilot مؤثر في مساحة معزولة.

- Goal→خطط/patch proposals→critic→runner مستقل→دليل نتيجة→مراجعة بشرية→تطبيق محدد عبر الحد المحمي فقط. القيود تشمل الملفات والأفعال وعدد المحاولات والوقت والكلفة؛ إلغاء وانتهاء واضحان.
- كل تقييم يربط البايتات الفعلية والـsuite والبيئة والخروج بالمرشح؛ لا يمنح `REPORTED_CHECKS_MET` الحالي صدقًا تنفيذيًا تلقائيًا. حفظ خطط وتبريرات مختصرة قابلة للمراجعة، لا استدلال داخلي خاص.
- **القبول:** مهمة حقيقية من corpus: RED ثم patch ثم GREEN، وعدم تعديل اختبارات القبول الأصلية؛ approval قديم أو معدل DENY؛ لا rollback يفقد تعديلًا خارجيًا أو يحيي authorization.
- **التراجع:** وقف التطبيق والعودة إلى advice-only، مع استعادة محكومة عند الحاجة. لم يتحول نجاح تجربة إلى تفويض جميع المستودعات أو فتح التنفيذ العام.

<a id="p13"></a>
### P13 — واجهة تشغيل لا تسبق الأمان

**المالك:** Frontend + Backend. **التبعية:** P12. **المسارات:** `dashboard/src/` وdashboard server وCLI؛ reuse للعقود لا إعادة حساب قرار السلطة في المتصفح.

- عرض goal/candidates/failed/missing reports، والتفريق بين «التحليل اكتمل» و«تم التنفيذ» و«بانتظار موافقة». روابط الأدلة وحالة الكتالوج من backend، لا أرقام demo.
- مصادقة واجهة وحدود جلسة وCSRF/origin عند استخدام cookies، وإبطال الموافقات القديمة؛ لا مفاتيح خدمة في المتصفح أو عاملة يقررها نموذج.
- **القبول:** E2E للنجاح والفشل والإلغاء وانتهاء الموافقة وعزل مستخدمين وانقطاع الاتصال؛ طلبات API نسبية، وإن استخدمت معاينة تربط الخادم بـ0.0.0.0 دون فتح origins عشوائيًا.
- **التراجع:** فصل الواجهة الجديدة؛ CLI الاستشاري يبقى صالحًا، لا تنفيذ عام من الواجهة القديمة.

<a id="p14"></a>
### P14 — تعلّم فعلي أولًا ثم Shadow

**المالك:** ML + Evaluation. **التبعيات:** P11/P12 وبيانات فعلية مرخصة ومراجَعة كافية؛ ليس مجرد مرور وقت.

- reuse للمتعلّم ML/DL الحالي؛ جمع observations حقيقية، identity موثوق للمراجع، منع duplicates/poisoning/leakage، وإدارة موافقة البيانات وحذفها.
- الحفاظ على بوابات الكمية وتغطية المجموعات والاستراتيجيات والفصل، ثم تقييم كفاية إحصائية ومعايرة/drift مستقلة؛ 120 عينة حد برمجي لا شهادة جودة.
- **القبول:** candidate مقابل baseline على holdout مستقل لم يُستهلك باختيار متكرر؛ درجات uncalibrated لا تقدم كثقة. shadow بلا أثر، ثم اعتماد منفصل إن استوفى معايير التجربة المثبتة.
- **التراجع:** سحب النموذج إلى baseline؛ التعلم لا يختار نفسه ولا يوافق على COMMIT. لا تحويل بيانات fixtures إلى خبرة مستخدم أو تسمية ذلك RLHF/LoRA.

<a id="p15"></a>
### P15 — معرفة وقواعد وFormal بنطاق محدد

**المالك:** Knowledge + Formal + QA. **التبعية:** P11؛ use case وADR للأداة الفعلية.

- claims بمصدر وتاريخ وثقة، استرجاع وتعارض وabstention؛ rules/constraints ذات schema؛ graph/ontology عند ضرورة مثبتة، لا قاعدة عامة باسم محرك.
- solver فعلي عبر port محكوم، وحد timeout ونموذج/فرضيات محددان؛ لا تحويل heuristics القديمة إلى إثباتات بالتسمية.
- **القبول:** SAT يعطي counterexample، وUNSAT نتيجة مقيدة بالنموذج، وUNKNOWN/timeout غير حاسم؛ fixtures متناقضة ومصادر مزورة وخواص دنيا مثبتة.
- **التراجع:** تعطيل المكوّن أو إرجاع «غير معلوم»؛ لا صلاحية من claim أو برهان خارج نطاقه.

<a id="p16"></a>
### P16 — وكلاء ومسارات متعددة بعد baseline أحادي

**المالك:** Agent + Evaluation. **التبعيات:** P11/P12؛ P14 إضافية إذا استُخدم scorer متعلّم.

- Tree/Graph search وensemble/debate/voting والـroles تجارب منفصلة فوق نفس عقود السلطة، مع حدود عدد الفروع والرسائل والموارد ومصدر الأدلة.
- **القبول:** مقارنة عادلة بنفس ميزانية الوقت والكلفة على مهام مستقلة؛ قيمة إضافية مقاسة، وعدم تضخيم الثقة بمصدر مكرر أو منح authority بالتصويت. نموذج العالم/simulation لا يدّعي قياسًا حيًا دون مصادر.
- **التراجع:** الرجوع للمسار الأحادي؛ لا تغيير النواة أو تعليم الوكلاء منح أنفسهم صلاحيات.

<a id="p17"></a>
### P17 — التقنيات المتخصصة: برنامج تجارب لا وعود أسماء

**المالك:** ML/Formal/Infrastructure بحسب البند. **التبعية الدنيا:** P11؛ لكل بند تبعيات إضافية من ADR، وP14 عندما يتطلب بيانات تدريب، وبيئة عتاد مستقلة عند الحاجة.

- **نموذج/runtime:** MoE وKV tensors وquantization/pruning/LoRA/adapters/distillation تحتاج نموذجًا ومحركًا متوافقين؛ لا تنفذها طبقة API عامة بمجرد إضافة flag.
- **تدريب/خصوصية/عتاد:** RL/RLHF/DPO/Federated/DP/TEE/enclave لها بيانات وتراخيص وميزانيات وthreat models واختبارات خاصة؛ لا تشابه نصي مع FedAvg أو sandbox يساوي تنفيذها.
- **استدلال متخصص:** causal/spatial/counterfactual/theorem/program synthesis تحتاج مهمة ونموذجًا ومصدر حقيقة وتقييمًا؛ لا احتمالات عشوائية أو prefix rules كدليل.
- **مخرج كل تجربة:** فرضية فائدة، baseline، بيئة/إصدار، artifact، قياس، كلفة، خطر، ثم GO محدود أو NO_GO معلل. **التراجع:** عزل التجربة وإبقاء البند غير مفعّل. التغطية موثقة لكل ID في الخريطة، لا سقوط لأي اسم من القائمة.

<a id="p18"></a>
### P18 — مراجعة إصدار محدود، والنشر بوابة مستقلة

**المالك:** Security + QA + SRE، مع مراجعة اعتماد مستقلة عن منفذ التغيير. **التبعيات:** P03/P07/P12/P13، وقبول جميع المكونات التي فُعلت فعليًا.

- P09 إلزامية إذا استخدم المنتج DB، وP14 إذا فُعل scorer متعلّم؛ أي تقنية اختيارية في النطاق تحتاج قبولها. لا نجعل باقي الـ200 شرطًا مخفيًا أو ندعي تنفيذها.
- **القبول:** H1/H2/H3 والانحدار القديم والجديد و`verify` إلى نهايته GREEN، لا skipped/cancelled/todo تستر إخفاقًا؛ اختبار البيئة المستهدفة وownership والعزل والأسرار وتمرين استعادة وkill switch وحمل ضمن حدود مثبتة ومراقبة فعلية.
- وثيقة نطاق ودليل أدلة وتشغيل واستجابة حوادث وتراجع، وإقرار المخاطر الباقية. الصياغة: **اجتازت الفحوص الحالية ضمن هذا النطاق**، لا «بلا أخطاء».
- نجاح المراجعة يسمح بطلب موافقة إصدار/بيئة محددة فقط. لا merge أو deployment أو migration حية تلقائية. **التراجع:** وقف الآثار والموصلات واستعادة مختبرة، دون إحياء سلطة مستهلكة أو مسح دليل.

## 5. عقد التسليم الإلزامي لكل حزمة

كل بطاقة تصبح تغييرات صغيرة قابلة للمراجعة، مع السجل التالي:

1. ID والنطاق وغير المشمول، المالك والمراجع، والتبعيات والأذونات البيئية.
2. hashes الشفرة/الاختبارات/العقود قبل العمل؛ لا تعديل RED قائم. اختبارات جديدة تغيّر العدّ الكلي ويعاد قياسه.
3. RED حقيقي أو دليل فجوة، ثم إصلاح أدنى، ثم **نفس** الاختبار GREEN مع control موجب؛ التفسير ليس بديلًا عن التشغيل.
4. أوامر/بيئة/exit codes/نتائج خام وبصمات filesystem أو DB وسجلات العملية المناسبة، لا snapshots مزخرفة بنتائج mock. الأدلة الحساسة خارج Git وبصلاحيات مقيدة؛ داخل Git ملخص منقح وبصمات ومراجع، بلا أسرار.
5. targeted regression ثم full verify. في P01 يبقى H3 معروفًا مؤقتًا؛ بعد P02/P03 لا اعتماد تنفيذ دون GREEN كامل. لا استخراج جزء ناجح من سجل فاشل كقبول شامل.
6. خطة disable/rollback واسترداد اختبرت؛ توقيع/بيانات تعلم/تقرير اختبارات لا تتحول إلى permission.
7. تحديث الخريطة والكتالوج **بعد** دليل النطاق الفعلي، مع فصل maturity عن integration عن live proof. لا تغيير M/P/D/N أو CONNECTED لمجرد إنشاء ملف.
8. العمل على فرع الجلسة نفسه؛ commit مستقل لكل حزمة عند الإذن، دون تبديل فروع أو merge/deploy تلقائيين.

## 6. أوامر البدء بعد الموافقة — ليست منفذة هنا

P00، من جذر المستودع، مع حفظ stdout/stderr وexit codes في دليل أدلة خارجي خاص:

```bash
git status --short
node --version
npm --version
node --test tests/celia-system.test.js tests/celia-learning.test.js
node --test tests/celia-workspace-commit-persistence.test.js tests/celia-workspace-commit-auth.test.js tests/celia-workspace-commit-http.test.js tests/celia-workspace-http.test.js tests/celia-workspace-write-auth.test.js
npm run verify
```

لا توقف حفظ الأدلة أو تفسير النتائج لمجرد أن `verify` يعيد 1 على baseline المعروف. الهدف التالي P01 وحدها:

```bash
node --test --test-name-pattern='COMMIT H2:' tests/celia-workspace-commit-hardening.test.js
```

ثم تعديل أدنى في المسار المصرح به، ثم نفس الأمر، ثم H1 والانحدار الكامل والفحص الشامل. تشغيل اختبار بفلتر هدفه العزل التشخيصي؛ نتائجه لا تحل محل تشغيل كامل بلا فلتر. P02 تبدأ بحزمتها وRED الأصلي بعد إغلاق P01، لا بإصلاح جانبي داخلها.

**صيغة أمر البدء المقترحة:** «ابدأ P00 ثم P01 فقط، مع إبقاء الاختبارات السابقة بلا تعديل، وتوقف عند أي توسع لازم في العقد أو مشكلة استعادة؛ سلّم RED→إصلاح→GREEN والانحدار والأدلة، دون الانتقال تلقائيًا إلى H3 أو create أو Supabase أو نشر».

## 7. الموارد والقرارات قبل كل بوابة

لا ميزانية أو فريق أو مواعيد ملزمة معتمدة؛ لذلك هذه **خطة عمل مرتبة لا وعد زمني**. إذا كان المنفذ شخصًا واحدًا تُنفذ حزم الكود بالتتابع، مع مراجعة أمنية مستقلة قبل اعتماد الآثار. يعاد تقدير الجهد بعد P00، وبعد ADR الخاص بـH3، وبعد اختيار بيئة العزل؛ البيانات الحقيقية والعتاد لا تكتمل بمرور عدد أسابيع.

| القرار | آخر نقطة لحسمه | الافتراضي حتى الحسم |
|---|---|---|
| نموذج الكاتب الخارجي وfilesystem والملكية القابلة للفرض | P02 | COMMIT غير معتمد |
| عزل runner وعدد workers/tenants وسقوف الموارد | P05/P06 | لا تنفيذ؛ تخطيط محلي محدود |
| هوية المالك والأدوار وسياسة الاحتفاظ/الحذف | P04/P06 | لا توسيع مشاركة البيانات |
| local store أم Supabase وبيئة الاختبار | P08 | لا DB حية أو migrations |
| provider/model والبيانات المسموح إرسالها وسقف الإنفاق | P10 | لا اتصال مدفوع أو إرسال كود تلقائي |
| معيار جودة الإصلاح والتكلفة/الزمن وعدم التراجع | P11 قبل التجارب | لا اعتماد نتائج على عتبات لاحقة |
| حقوق بيانات التدريب والمراجعين ومقياس التحسن | P14 | جمع مصرح به فقط؛ لا auto-training/promotion |
| الحاجة لترخيص/عتاد لكل تقنية متخصصة | P17 | مسار مؤجل ظاهر، لا تنفيذ وهمي |
| المستودع/البيئة/المستخدمون المسموحون للإصدار | P18 | لا merge/deploy أو تعرض عام |

**حالة هذه الجولة:** إعداد الوثائق والخريطة والتحقق من اتساقهما فقط. لم تبدأ حزمة إصلاح، ولم تتغير الشفرة أو الاختبارات أو صلاحيات التشغيل، ولم تُفعّل أي تقنية ناقصة.
