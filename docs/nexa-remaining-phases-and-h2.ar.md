# المتبقي: مراحل التنفيذ ونتيجة حزمة H2 المحدودة

**التاريخ:** 20 سبتمبر 2026 — **القرار العام: HOLD، لا نشر ولا دمج.**

استجابةً لطلب «قسم المتبقي إلى مراحل ونفذ»، نُفّذ تثبيت baseline جديد ثم إصلاح H2 المحدد، دون الجمع بين إصلاحي H2 وH3. هذه الوثيقة تحديث تنفيذي للخطة ذات [19 حزمة](nexa-execution-plan.ar.md)، لا استبدال لسجلها التاريخي ولا إذن بتنفيذ المراحل اللاحقة دون بواباتها.

## 1. ما نُفّذ الآن

- إعادة اختبار H2 الأصلي: **RED → تحديد السبب → إصلاح محدود → نفس الاختبار GREEN**. لم يُعدّل الاختبار أو fixture الأصلي.
- إضافة **10 اختبارات** على ملفات فعلية وتفويضات موقعة وسياسة سماح حقيقية، مع حقن أخطاء I/O محدود؛ ليست محاكاة لقرار السماح أو منعًا لكل الطلبات.
- أثناء المراجعة ظهر خلل إضافي في استعادة بتات الصلاحيات: اختبار جديد **RED ثم GREEN** بعد إصلاحه؛ بقيت توقعاته كما هي.
- تشغيل الانحدار المستهدف ثم الكامل ومقارنة بصمات الملفات السابقة وحفظ الأدلة.
- **تغير ملف تنفيذ سابق واحد فقط:** `tools/celia-workspace-commit-port.mjs`. أضيف `tests/celia-workspace-commit-h2.test.js` وهذا التقرير وحزمة الأدلة.

**الوصف المقبول:** اجتازت معالجة H2 المحدودة الفحوص الحالية. هذا ليس إغلاقًا عامًا للذرّية أو سلامة COMMIT: حظر الاسترجاع الفاشل محلي للعملية، وH3 ما زال RED، والتعافي بعد الانقطاع غير مثبت.

## 4. السبب والإصلاح

كان التطبيق يكتب الملفات تباعًا بعد التحقق واستهلاك التفويض، بلا مسار undo يحتفظ بالصور السابقة. إذا نجحت كتابة A ثم فشلت B بقي الجذر مختلطًا.

الإصلاح في المنفذ المحدود:

1. الاحتفاظ بالـpreimages ضمن الحدود الموجودة، دون تغيير descriptor الموقع أو توسيع المنحة.
2. تسجيل كل محاولة كتابة **قبل** استدعائها، لأن الاستدعاء الذي يرمي خطأ قد يكون كتب جزءًا من الملف بالفعل.
3. تسجيل الأدلة المنشأة فعلًا واحدًا واحدًا؛ لا حذف recursive أثناء الاسترجاع.
4. عند الخطأ: استعادة البايتات وبتات mode للملفات السابقة، وإزالة الملفات الجديدة والأدلة الخاصة الفارغة. لا حذف ملف منافس عند فشل `wx` بـEEXIST.
5. إذا نجح الاسترجاع: إعادة الخطأ الأصلي مثل ENOSPC؛ **لا ردّ التفويض المستهلك**.
6. إذا فشل الاسترجاع: `503 COMMIT_RECOVERY_REQUIRED`، والسبب محفوظ داخليًا، وحظر لكل committer لنفس الجذر **في العملية الحالية**. التحقق من الهوية يسبق هذا الحظر؛ الطلب المجهول يبقى 401.

**حالة mode الإضافية:** على هذه البيئة أسقطت الكتابة البت الخاص من `04640` إلى `00640` لملف اختبار مملوك وغير قابل للتنفيذ. خيار mode في writeFileSync لا يعيد صلاحيات ملف موجود. أظهر `mode-red.tap` الفرق، ثم أصلحنا إعادة mode بعد آخر كتابة والتحقق منه؛ نفس التوقع نجح في `mode-green.tap`.

## 6. حدود لم تُغلق — سبب HOLD

- **H3 ما زال يفشل فعلًا:** العملية الخارجية تعدل A بعد التحقق، ثم يمحو COMMIT تعديلها ويطبق A وB ويرجع ALLOW بدل DENY 403. سجل PID والتدخل والكتابة موجود في `hardening-final.tap`. لم يُعدّل الاختبار أو يُحجب hook.
- **فشل الاسترجاع قد يترك جذرًا جزئيًا.** الحظر الجديد يمنع محاولات لاحقة داخل العملية، لكنه لا يُحفظ على القرص؛ restart يزيله. اختبار restart المار يخص **استرجاعًا ناجحًا وبقاء التفويض مستهلكًا**، وليس استمرار عزل استرجاع فاشل. لا يُستخدم restart إجراءً آمنًا لتجاوز الحظر.
- يفترض الاسترجاع ملكية حصرية للجذر؛ لا نفرض هذه الملكية ضد كاتب خارجي بهذا الإصلاح. لذلك لا نسميه transaction ذرية متعددة الملفات، ولا حماية من تغييرات خارجية أثناء undo.
- لا atomic visibility للقراء؛ لا SIGKILL/power-loss recovery مثبت، ولا ضمان عام لتعدد العمليات. لم نضف سجل recovery دائمًا أو بروتوكول fsync لهذا النطاق.
- لا نَعِد بإعادة root ctime/mtime أو كل metadata كما كانت بعد كتابة حقيقية واسترجاعها؛ القياس يحفظ المحتوى وtopology وmode، وmetadata الخاصة بـstaging كما يقيسها الاختبار، وليس atime.
- لا نجاح مستنتج لـcreate أو legacy rollback أو Supabase، ولا إثبات نشر. النظام الاستشاري ما زال بلا تنفيذ مؤثر، والتعلم candidate-only.

**الحالة:** اجتياز قبول H2 الأصلي المحدود، لكن **ليس اعتمادًا أمنيًا نهائيًا لـH2/recovery أو COMMIT**. التالي حزمة H3 مستقلة بقرار تصميم قابل للفرض؛ لا تكفي lock تعاونية أو rehash أخير أو rename منفرد. العزل الدائم للجذر غير المؤكد شرط إغلاق recovery قبل أي تشغيل إنتاجي.

## 7. خطة التراجع

- عند خطأ تطبيق ناجح الاسترجاع: حفظ الخطأ والأدلة، وإبقاء التفويض مستهلكًا؛ إعادة المحاولة تتطلب منحة جديدة.
- عند `COMMIT_RECOVERY_REQUIRED`: إيقاف استخدام الجذر غير المؤكد، حفظ الأدلة، واستعادة يدوية معتمدة بعد فحصه؛ لا إعادة تشغيل لتجاوز الحظر ولا مسح سجل H1.
- إن تقرر الرجوع عن هذا التغيير البرمجي بإذن مستقل: تعطيل الاستخدام المؤثر أولًا، والتحقق من بصمات الحزمة، ثم استعادة **ملف المنفذ وحده** من `port-before.txt`. لا git reset أو محو تغييرات المستخدم أو تعديل الاختبارات القديمة. العودة للنسخة السابقة تعيد خلل H2 المعروف، ولا تجعلها صالحة للنشر.
- لم ننفذ commit أو push أو merge أو deploy أو live migration، ولم نفتح أي بوابة.
