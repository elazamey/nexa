# COMMIT — دليل الإصلاح المحدود RED → GREEN

> **حزمة H1-PERSISTENCE — قياس مرحلتها:** [الدليل والحدود التشغيلية](celia-workspace-commit-h1-persistence.ar.md). H1 الأصلي و20 اختبار استمرارية و39 اختبارًا سابقًا نجحت. H2 وH3 ما يزالان RED. verify في تلك الحزمة: **374 PASS / 2 FAIL من 376**. يلزم مخزن استهلاك دائم خارج root؛ التفاصيل التاريخية أدناه لا تعني اجتياز الحدود الثلاثة الآن.

**التاريخ:** 20 سبتمبر 2026  
**بيئة القياس:** Node v22.22.3 / npm 10.9.8  
**العقد:** [Celia COMMIT v1](celia-workspace-commit-contract.ar.md).  
**النطاق:** حد HTTP لتطبيق ملفات staging فقط؛ لا Git commit أو merge أو deploy، ولا إصلاح لـcreate أو Supabase.

> **تحديث لاحق للحدود:** اختبارات [H1/H2/H3](celia-workspace-commit-hardening-red.ar.md) أصبحت RED بدليل عمليات حقيقية: replay بعد restart في حالة ABA، وتطبيق جزئي عند عطل الملف الثاني، وطمس تعديل كاتب خارجي. اختبارات العقد السابق أُعيدت ونجحت 39/39 مع WRITE؛ رقم 353/353 أدناه يخص جولة GREEN السابقة، لا اجتيازًا حاليًا لحدود hardening.

## 1. ما تغيّر

- [بوابة COMMIT المستقلة](../tools/celia-workspace-commit-auth.mjs): تحقق الهوية والتوقيع والزمن، ثم capability من مُصدر موثوق والفعل والمورد والقيود والسياسة والاستخدام الأحادي.
- [منفذ COMMIT المقيد](../tools/celia-workspace-commit-port.mjs): يحسب snapshot الحالي لـstaging وملفات base، يقارن البصمتين، ثم يطبّق البايتات التي تحقق منها.
- [معالج HTTP](../tools/celia-dashboard-server.mjs): يقرأ إعداد `CELIA_WORKSPACE_COMMIT_AUTH` المستقل، ويستدعي المنفذ المقيد بدل `workspacePort.commit()` القديم، ويسجل حدث النجاح. الجسم محدود بـ128 KiB.
- أضيفت [19 حالة تعاقدية](../tests/celia-workspace-commit-auth.test.js). امتد fixture المشترك بمعامل إعداد COMMIT اختياري فقط؛ لا استبدال للـverifier أو منفذ الملفات أو قرار السياسة.

لم يتغير `celia-workspace-write-auth.mjs` أو اختبارات WRITE أو اختبارات COMMIT RED الأصلية. لم يُفتح أي من بوابات النواة الست. المنفذ القديم موجود لمستخدميه الداخليين، لكن مسار HTTP المعالج لم يعد يمرّر التنفيذ إليه؛ هذا ليس تدقيقًا لكل منافذ الكتابة الأخرى.

## 3. عقد COMMIT اختُبر، وليس مجرد إغلاق شامل للمسار

### ALLOW حقيقي

جهز fixture ملفًا قائمًا وملفًا جديدًا متداخل المسار عبر WRITE مفوض، ثم:

1. حسب بصمة قائمة staging كاملة وبصمة base: المحتوى/الوجود/الصلاحيات للملفات المقابلة.
2. أصدر المشغّل grant أحادية الاستخدام للفعل `commit`، مقيدة بالـworkspace والجذر والبصمتين.
3. وقع principal الطلب وأرسله إلى الخادم مع سياسة تسمح له.
4. أعاد الخادم HTTP 200 و`changedFiles: 2`.
5. قارنت الاختبارات البايتات الفعلية في الجذر وstaging، لا الاستجابة وحدها.
6. ثبت عدم تغير staging والملفات الأخرى؛ تغيرت فقط الملفات المعتمدة والمجلد المطلوب إنشاؤه وmetadata ذات الصلة في الجذر.
7. ظل mode الملف القائم في الحالة المختبرة `0640`؛ الملفات الجديدة تُنشأ بـ`0600` مع أثر umask النظام، دون نسخ صلاحيات staging.
8. ظهر حدث `WORKSPACE_COMMIT` يحمل principal وcapabilityId وpolicy rule وبصمتي الحالة ومرجع الطلب، ويطابق `evidenceEventHash` العائد.

الحدث هنا سجل داخل الذاكرة غير موقع، وليس إيصال NEXA أو دليلًا دائمًا؛ دوره ربط نتيجة التنفيذ بالتفويض الذي استُخدم.

### DENY مستقل

نجحت الحالات الجديدة في رفض:

- مجهول → 401، وهوية موقعة دون capability → 403.
- WRITE capability داخل envelope موقعة للفعل COMMIT → 403.
- **COMMIT grant فعلية لـA** مع محاولة B: مرة بتغيير workspace في الطلب، ومرة بإعادة توقيع descriptor الصحيح لـB مع إبقاء grant الخاصة بـA.
- grant منتهية داخل envelope جديدة.
- إعادة الطلب نفسه بعد نجاحه، وenvelope جديدة تحاول إعادة استهلاك grant نفسها.
- تغيير staging عبر WRITE مفوض بعد إصدار COMMIT authorization.
- إعادة توقيع بصمة staging الجديدة مع إبقاء grant المرتبطة بالبصمة السابقة.
- إضافة ملف إلى staging أو حذف ملف منها بعد الموافقة.
- تغير محتوى ملف base أو صلاحياته، أو ظهور ملف كان غائبًا وقت التفويض.
- grant وطلب يستهدفان جذرًا آخر.
- capability صحيحة مع سياسة فارغة، أو غياب المُصدرين الموثوقين.
- حامل أو audience مختلفان، توقيع متلاعب به، أو فعل/مورد خاطئ.
- غياب قيود الحالة المطلوبة أو ميزانية استعمال أوسع من واحد.
- symlink في ملف staging أو ملف الهدف قبل التطبيق.
- طلبان متزامنان بgrant واحدة: **200 و403، وحدث COMMIT واحد فقط**.

كل رفض يُقارن فيه snapshot للجذر كاملًا بما فيه staging، وmetadata لمجلد الجذر نفسه، وحالة workspace، وأحداث COMMIT. تشمل المقارنة المحتوى والأسماء والصلاحيات والملكية وmtime/ctime؛ يستثنى atime لتأثره بقراءة snapshot.

## 5. حدود GREEN

GREEN هنا لحد التفويض المرتبط بالحالة وفق السيناريوهات المختبرة، لا لجاهزية المنتج كله:

- expectedBaseHash يغطي ملفات الجذر المستهدفة فقط، وليس Git HEAD أو المستودع بأكمله.
- لا `await` بين التقاط البايتات والتحقق والتطبيق: يمنع تداخل طلبات العملية الواحدة، لا سباق كاتب خارجي على filesystem. يفترض التنفيذ جذرًا حصريًا للعملية.
- تطبيق عدة ملفات ليس transaction ذرية؛ عطل I/O قد ينتج أثرًا جزئيًا و500، مع بقاء grant مستهلكة. لا يُسمى ذلك DENY بلا أثر.
- replay وميزانية الاستخدام داخل الذاكرة؛ لا ضمان عبر restart أو عدة instances. يلزم تغيير audience وعدم إعادة استخدام grants بعد restart في التشغيل التجريبي؛ التنسيق الدائم لاحقًا.
- create/rollback ومسارات أخرى ما زالت خارج الإصلاح، وكذلك نموذج ملكية Supabase وسياسات RLS والـconnector الحقيقي.
- بعض ضوابط الحدود، مثل الحد الأقصى للملفات والبايتات، مطبقة لكن ليست كل تركيباتها ضمن هذه الحزمة الاختبارية؛ لا ادعاء بتغطية كاملة.

**التراجع الآمن:** إزالة إعداد COMMIT وإعادة تشغيل الخادم تعيدان رفض COMMIT افتراضيًا؛ لا تعُد إلى الاستدعاء القديم غير المفوض. تعطيل التفويض لا يعكس ملفات سبق تطبيقها. يبقى منع النشر العام قائمًا.
