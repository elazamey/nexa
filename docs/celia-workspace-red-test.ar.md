## السيناريو ومعيار القبول

1. نسخ ملفات المصدر اللازمة إلى مجلد مؤقت مستقل، لأن خادم Celia يحدد جذر الملفات من موقع ملفه، وليس من `cwd` فقط.
2. تشغيل نسخة الخادم بمعالجات HTTP ومنفذ ملفات حقيقيين، مع نقل الاستماع فقط إلى loopback ومنفذ عشوائي. لا تُعدّل استجابات API ولا يُحاكى قرار التفويض.
3. إنشاء workspace موجود عبر مسار create الحالي كتهيئة للاختبار، ثم وضع ملف مراقبة في staging وملف مقابل في الجذر المؤقت.
4. أخذ بصمات الملفات وبنية المجلدات قبل الطلب.
5. إرسال `POST /api/v1/workspace/write` دون `Authorization` أو cookie أو capability أو `evidenceRef`.
6. اشتراط **401 أو 403**، وعدم الإبلاغ عن نجاح، وعدم تغير ملفات أو مجلدات الجذر المؤقت بما فيه staging.

**مهم:** السماح الحالي بإنشاء workspace دون مصادقة ليس سلوكًا معتمدًا. هذه تهيئة مؤقتة لعزل فحص write عن أخطاء «workspace غير موجود». عند تأمين create يجب استبدالها بتهيئة مفوضة أو منفذ تهيئة خاص بالاختبارات؛ رفض create وحده لا يُحسب نجاحًا لاختبار write.

## نتيجة التشغيل الفعلية

```bash
node --test tests/celia-workspace-http.test.js
```

**فشل اختبار الأمان كما هو مقصود في مرحلة Red:**

- الاستجابة الفعلية: **HTTP 200** و`ok: true`.
- تغير ملف `authorization-canary.txt` داخل `.nexa/staging/<workspaceId>/` في المجلد المؤقت.
- المطلوب: رفض الطلب دون تغيير الملفات.
- رمز خروج الاختبار: **1**.

هذا فشل تحقق أمني، لا فشل إقلاع أو استيراد أو اتصال. لم يُستدعَ commit، ولا تثبت هذه الحالة وحدها سلوك commit أو حماية المسارات أو تفويض مستخدم مسجل بصلاحيات ناقصة.

## احتواء التجربة وتنظيفها

- لا تشغيل لخادم preview عام؛ الخادم قصير العمر ويستمع محليًا داخل عملية الاختبار فقط.
- نسخ المصدر دون `.git` أو الملفات المخفية أو `node_modules` أو الروابط الرمزية.
- لا توريث مفاتيح الخدمات أو `NODE_OPTIONS`؛ إعداد Supabase في وضع mock صريح.
- مهلة للإقلاع والطلبات والاختبار؛ معرفة الجاهزية عبر IPC بدل انتظار زمني ثابت.
- إيقاف العملية الفرعية وحذف المجلد المؤقت حتى عند فشل assertion؛ خروج الخادم عند انقطاع IPC أيضًا.
- بعد التشغيل، لم يبق خادم الاختبار أو مجلده المؤقت، ولم يُنشأ `.nexa` في checkout.

هذا عزل عملي للسيناريو الحالي، وليس sandbox نظام تشغيل يُضمن به احتواء شفرة غير موثوقة عمومًا.

## الخطوة التالية

إضافة عقد المصادقة والتفويض والرفض الافتراضي لمسارات workspace، مع تهيئة اختبار مفوضة لمساحة العمل. ثم تحويل هذا الاختبار إلى أخضر **بمنع الكتابة غير المفوضة فعليًا**، وإضافة حالات create/commit والدليل المزور وحدود الملفات. لا تعطيل للاختبار ولا تخفيف لمعيار عدم الأثر الجانبي.
