## 1. موضع الحماية وترتيبها — قراءة الشفرة

- `tools/celia-dashboard-server.mjs:59–63`: إعداد موثوق يملكه المشغّل؛ غياب الإعداد يستخدم `{}`، لا صلاحية مستمدة من جسم الطلب أو headers.
- `tools/celia-workspace-write-auth.mjs:33–58`: قوائم issuers والسياسات فارغة افتراضيًا؛ غياب/عدم صحة إثبات الهوية يعطي 401، ومخالفة audience تعطي 403.
- الملف نفسه `:71–104`: ربط المورد بـworkspace/path، وتوقيع intent الذي يتضمن POST والمسار والمحتوى؛ capability صحيحة من issuer موثوق وبفعل write ونطاق exact، ثم policy ALLOW. التوقيع وحده غير كافٍ.
- الملف نفسه `:106–113`: حجز replay/use budget تزامنيًا قبل استدعاء I/O؛ لا إنفاق متزامن للمنحة ذات الاستخدام الواحد في العملية الحالية.
- `tools/celia-dashboard-server.mjs:749–753`: `authorizeWorkspaceWrite(input)` يسبق `workspacePort.writeFile(...)`؛ لا استدعاء لمنفذ كتابة الطلب عند رفض التفويض.

هذا وصف للمسار المقروء من الشفرة. عدم تغيّر filesystem قيس تشغيليًا كما يلي؛ لا نزعم أن مقارنة البصمات وحدها تتتبع كل filesystem read أو syscall.

## 2. الدليل التشغيلي — نفس الاختبارات بلا تغيير

```bash
node --test tests/celia-workspace-http.test.js tests/celia-workspace-write-auth.test.js
```

النتيجة **17/17، exit 0**. السطر التشخيصي الأصلي:

```text
Anonymous write returned HTTP 401; changed paths: []
```

| الحالة | القبول الذي اجتاز فعليًا |
|---|---|
| طلب كتابة بلا هوية | 401، لا نجاح، لا تغيير في الملفات أو الأدلة أو metadata المختبرة |
| هوية موقعة بلا capability | 403، دون أثر |
| إعداد خادم غائب أو policy/issuer list فارغة | DENY حتى مع طلب موقّع؛ لا ALLOW افتراضي |
| إثبات مزور/قديم، issuer غير موثوق، presenter/audience خاطئ | رفض وفق العقد، دون كتابة |
| تعديل workspace/path/content خارج التوقيع | 403 دون تغيير |
| scope/action/expiry أو constraints مخالفة | رفض دون أثر |
| إعادة الطلب الناجح أو تجاوز استخدام المنحة داخل العملية | لا أثر ثانٍ؛ طلبان متزامنان لمنحة استخدام واحد يعيدان 200 و403، وعدّاد كتابة واحد |
| **control موجب بتفويض صحيح** | HTTP 200 وكتابة بايتات فعلية/إنشاء ملف داخل staging فقط؛ ملف root المقابل لا يتغير |
| مدخلات path غير صالحة أو جسم أكبر من الحد | 400 أو 413 وفق العقد، دون أثر؛ ليست تحويلًا للرفض الأمني الصحيح إلى 500 |

الاختبار الأصلي يقارن المحتوى وtopology. اختبارات التفويض الإضافية تقارن أيضًا modes والملكية وmtime/ctime وعدادات workspace وحقول metadata الأخرى عبر `snapshot`، باستثناء atime الذي قد يتغير بالقراءة. الـcontrol الموجب يتحقق من اقتصار التغييرات على ملف staging وmetadata المسموحة له ولدليله.

المعالجات وقرارات التفويض ومنفذ الملفات حقيقية في نسخ مؤقتة معزولة من المصدر؛ ليست استجابات mock. الخادم يختبر على loopback داخل fixture ولا يفتح preview عامًا أو يكتب في root المستودع الحي. تهيئة الاختبارات تستخدم create القديم لإعداد workspace موجود؛ **لا يحتسب ذلك قبولًا لأمان create**.

## 5. ما لا تغطيه النتيجة

- الحماية المثبتة هي `/api/v1/workspace/write` بعقده الحالي؛ ليست شهادة لكل internal port أو route.
- create وrollback وقراءة metadata وCOMMIT مستقلة؛ لا يُمنح أي منها PASS من نجاح WRITE.
- replay/use ledger الخاص بـWRITE داخل العملية؛ لم تثبت هذه الجولة استمراريته عبر restart. استمرارية COMMIT H1 منفصلة.
- لا ضمان شامل ضد جميع سباقات filesystem أو writer خارجي أو هروب symlink أو انقطاع الطاقة من فحوص التفويض وحدها.
- لا تصديق RLS أو تفعيل Supabase، ولا إصلاح H2/H3، ولا فتح للبوابات أو جاهزية نشر عام.
