# Celia workspace/commit — دليل RED مستقل

> **سجل تاريخي لمرحلة RED.** أُصلح حد COMMIT لاحقًا وفق [عقد مستقل](celia-workspace-commit-contract.ar.md)، ونجحت الاختبارات الثلاثة نفسها دون تعديل. كانت نتيجة تلك الجولة **353/353** وفق [دليل COMMIT GREEN](celia-workspace-commit-green.ar.md). أضيفت بعدها اختبارات [H1/H2/H3 وفشلت](celia-workspace-commit-hardening-red.ar.md)، فلا يمثل الرقم السابق اجتياز hardening الحالي. ما يلي يحفظ نتائج ما قبل الإصلاح وحدودها.

**التاريخ:** 20 سبتمبر 2026  
**الحالة:** COMMIT RED مثبت محليًا، دون إصلاح تشغيلي في هذه الجولة.  
**ملف الاختبار:** [celia-workspace-commit-http.test.js](../tests/celia-workspace-commit-http.test.js).

## 1. نطاق العمل

- إضافة ثلاث حالات HTTP تستخدم الخادم ومنفذ الملفات الحقيقيين داخل نسخة مؤقتة معزولة.
- تجهيز staging حصريًا عبر `workspace/write` المفوض: توقيع Ed25519، capability من مُصدر موثوق، وسياسة WRITE صريحة.
- عدم تعديل خادم Celia أو منفذ الملفات أو بوابة WRITE أو اختباراتها أو fixture المشترك.
- لا تعديل لـcreate أو Supabase أو migrations؛ لا merge أو deploy.

هذا انتقال من **فجوة تفويض محددة من قراءة الشفرة** إلى **تنفيذ commit غير مفوض مثبت في البيئة المحلية لهذه الحالات**. لا يستنتج منه وجود نشر خارجي مكشوف أو وقوع اختراق فعلي.

## 2. إعداد fixture والتحقق من صلاحية التجربة

1. مفاتيح مؤقتة لمُصدر موثوق ومستخدمين A وB وaudience الخادم.
2. إعداد الخادم يمنح WRITE فقط؛ لا سياسة COMMIT ولا capability COMMIT.
3. استدعاء create القديم كتهيئة، وليس اعتمادًا لأمانه.
4. إنشاء ملف أصلي في الجذر المؤقت، مع التأكد من غياب ملف جديد آخر.
5. إرسال عمليتي WRITE مفوضتين عبر HTTP لإنشاء نسختي الملفين داخل staging.
6. إثبات نجاح كل WRITE بـHTTP 200 وبصمة الطلب الموقع، ثم قراءة المحتوى الحقيقي من staging.
7. إثبات أن الجذر لم يتغير بسبب WRITE، وأن workspace يحتوي تغييرين وعداد كتابة يساوي 2.
8. أخذ snapshots قبل إرسال COMMIT.

لم يكتب الاختبار محتوى staging مباشرة ولم يستبدل المنفذ الحقيقي بمحاكاة. الكتابة المباشرة في إعداد الاختبار تخص ملف الجذر الأصلي وملف المراقبة غير المستهدف فقط.

## 3. الحالات ونتائج التشغيل

```bash
node --test tests/celia-workspace-commit-http.test.js
```

| الحالة | المطلوب | الفعلي |
|---|---|---|
| COMMIT مجهول بعد WRITE مفوض | 401/403، الجذر وstaging وmetadata دون تغيير | HTTP 200، إنشاء ملف وتعديل ملف في الجذر المؤقت |
| COMMIT يحمل WRITE envelope صحيحة وجديدة | 403، دون تطبيق التغييرات | HTTP 200، إنشاء ملف وتعديل ملف في الجذر المؤقت |
| A يحمل WRITE grant تخص workspace-A ويطلب commit لـworkspace-B | 403، لا أثر على أي workspace أو الجذر | HTTP 200، تطبيق ملفي B على الجذر المؤقت |

**TAP:** 3 اختبارات، 0 ناجح، 3 فاشلة، لا skipped أو todo أو cancelled؛ **exit code 1**.

في الحالات الثلاث أبلغ الخادم `changedFiles: 2`، وأكد snapshot تغير الملفات نفسها؛ لم يُعتمد على ادعاء الاستجابة وحده. بقي محتوى staging وmetadata المفحوصة له دون تغيير، لكن ذلك لا يجعل العملية آمنة بعد تغير الجذر. تغيرت أيضًا حالة مقارنة workspace بالجذر بعد تطبيق التغييرات.

مثال مختصر من diagnostics للحالة المجهولة:

```text
status: 200
reportedChangedFiles: 2
filesystemChanges:
  commit-red-a-added.txt
  commit-red-a-added.txt::metadata
  commit-red-a-existing.txt
  commit-red-a-existing.txt::metadata
staging changedEntries: []
staging metadataUnchanged: true
```

### ما الذي تثبته حالة WRITE ≠ COMMIT؟

- الـcapability المستخدمة تمنح `actions: ['write']` فقط.
- تُنشأ envelope جديدة بعد التهيئة، بمعرف وnonce مختلفين عن طلب WRITE الناجح؛ ليست إعادة إرسال للطلب المستهلك.
- يتحقق الاختبار محليًا من التوقيع وصلاحية grant للكتابة، مع ميزانية متبقية، قبل إرسالها إلى commit.
- التنفيذ الحالي يتجاهل حقل authorization في commit؛ قبوله لا يعني أنه تحقق من capability ثم وسّعها.

**حد الدليل:** هذه حالة إساءة استعمال تصريح WRITE على مسار COMMIT، وليست اختبارًا لgrant صحيحة للعملية COMMIT. لا تعزل وحدها سبب الرفض المستقبلي بين اختلاف العملية ومسار HTTP وشكل عقد COMMIT.

### ما الذي تثبته حالة cross-workspace؟

تغييرات A وB مُجهزة بطلبات WRITE موقعة من هويتين مختلفتين وبـgrants لموارد مختلفة. أُرسل إلى commit طلب لـB مرفقًا بإثبات WRITE يخص A، ونُفذت تغييرات B في النسخة المؤقتة.

لكن create الحالي لا يثبت ملكية workspace في سجل موثق؛ لذلك تعبير A/B يصف إعداد fixture ومن وقّع الكتابات، ولا يدعي وجود نموذج ملكية خادم مكتمل. كما أن الطلب يخالف حدود العملية والـworkspace معًا؛ **اختبار COMMIT grant صالحة لـA لكنها موجهة إلى B يظل مطلوبًا بصورة منفصلة** بعد تعريف العقد.

## 4. دليل عدم الأثر المطلوب

المعيار ثابت في الاختبارات: رفض التفويض وعدم أي أثر؛ لم تُكتب التوقعات لقبول HTTP 200.

المقارنة تشمل:

- snapshot كاملًا للجذر المؤقت، بما فيه staging: أسماء الملفات والمجلدات، بصمات المحتوى، والروابط.
- mode، uid، gid، size، inode، nlink، mtimeNs وctimeNs.
- metadata لمجلد الجذر نفسه ولمجلد كل workspace، لكشف أثر إضافة الملفات.
- حالة workspace وعدد الكتابات والتغييرات قبل الطلب وبعده.
- snapshot مستقل لـstaging لكل workspace في حالة cross-workspace.

يُستثنى atime لأن قراءات التحقق قد تغيره. حالة workspace غير الموجودة أو الفارغة أو HTTP 500 لا تُحسب PASS. يتضمن assertion حالة الرفض والأثر الجانبي معًا.

## 6. العزل والقيود

- العملية الفرعية تستمع على loopback ومنفذ عشوائي؛ لا preview أو خادم عام.
- root المستخدم هو نسخة مصدر مؤقتة دون `.git` أو أسرار التشغيل، وليس checkout العمل.
- Supabase في وضع mock صريح؛ لا اتصال أو كتابة قاعدة بيانات.
- يوقف fixture الخادم ويحذف مجلده حتى عند فشل assertions.
- لم يُنفذ git commit؛ كلمة commit هنا تعني تطبيق ملفات staging عبر API.

## 7. الخطوة التالية المقترحة — عقد COMMIT ثم الإصلاح

قبل إصلاح المسار، عرّف تفويضًا مستقلاً يربط الهوية والمُصدر والسياسة بالفعل `commit` والـworkspace و**مجموعة التغييرات الدقيقة وبصماتها**، لا بمجرد معرفة workspaceId أو امتلاك WRITE grant.

ثم أضف أدلة مستقلة لـ:

1. COMMIT grant صالحة ضمن السياسة → تطبيق الملفات المتفق عليها فقط.
2. COMMIT grant تخص A على workspace-B → رفض دون أثر.
3. grant منتهية أو مُصدر/حامل غير صحيح → رفض دون أثر.
4. إعادة الطلب أو إعادة استهلاك صلاحية محدودة → رفض دون تطبيق ثانٍ.
5. تعديل قائمة الملفات أو بصمة staging بعد التفويض → رفض؛ لا تطبيق نسخة لم تُعتمد.
6. عقد عملية أو مورد خاطئ → رفض حتى مع توقيع صحيح.

هذه الحالات **لم تُنفّذ ولم تحصل على PASS** في هذه الجولة. الذرية والتعافي من النسخ الجزئي موضوع مستقل يجب ألا يوصف بالمكتمل بمجرد إصلاح authorization.

يبقى فصل العمل كما هو: COMMIT authorization، ثم CREATE authorization/containment، ثم بوابة صحة RLS وفق نموذج ملكية معتمد، وبوابة مستقلة للاتصال الفعلي بـSupabase.
