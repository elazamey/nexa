## 1. نطاق الدليل

العقد السابق أثبت تفويض COMMIT وربطه بحالة الملفات في عملية واحدة وجذر حصري لها. هذه التجارب تقيس ضمانات **لم يشملها ذلك العقد**: استهلاك التفويض عبر restart، وعدم ترك تطبيق جزئي بعد عطل، والكتابة الخارجية بين التحقق والتطبيق.

- استُدعيت `createWorkspaceCommitter` و`createWorkspaceCommitAuthorizer` ومنفذ workspace الحقيقي داخل عملية Node مستقلة ونسخة مصدر مؤقتة.
- جرى تجهيز staging عبر بوابة WRITE الحقيقية وgrants موقعة؛ لا حقن ALLOW أو محاكاة للسياسة أو التوقيع أو البصمات.
- هذه اختبارات للحد التنفيذي/auth في عمليات منفصلة، **وليست اختبارات نقل HTTP**. نتائجها `ALLOW` و`DENY` و`ERROR`؛ لم تُحوّل إلى HTTP 200/500 مصطنعة.
- لم تتغير ملفات الإنتاج أو اختبارات WRITE/COMMIT السابقة أو fixture المشترك؛ قارنت بصمات SHA-256 لـ11 ملفًا قبل العمل وبعده وكانت متطابقة.
- لا تعديل لـcreate أو Supabase، ولا merge أو deploy أو تشغيل خادم عام.

| الحد | المطلوب | ما حدث فعليًا |

| H1 — استهلاك دائم للتفويض | التفويض المستهلك يبقى مرفوضًا بعد restart | DENY في العملية الأولى، ثم ALLOW في عملية جديدة بعد استعادة حالة base المعتمدة |
| H2 — فشل أثناء تطبيق عدة ملفات | لا يبقى الجذر نصف مطبق بعد فشل العملية | `ENOSPC` على الملف الثاني؛ A جديد وB قديم |

بقي staging دون تغيير في الحالات الثلاث. التأكيد يستند إلى قراءة ملفات الجذر وsnapshots، لا نتيجة الدالة وحدها.

## 3. H1 — Restart + ABA، لا ادعاء بأن كل restart يسمح بالـreplay

### السيناريو

1. إعداد ثابت للمُصدر والـprincipal والـaudience، مع grant COMMIT أحادية الاستخدام وطلب موقع صالح لمدة 300 ثانية.
2. COMMIT أول ناجح فعليًا؛ الجذر يطابق البايتات المعتمدة.
3. إعادة **بايتات base الأصلية فقط** بواسطة fixture، مع التأكد أن `expectedBaseHash` و`changeSetHash` وscope تطابق الطلب الأصلي تمامًا.
4. إرسال الطلب نفسه في العملية القديمة: **DENY 403**، والجذر لا يتغير. هذا control يثبت استهلاك grant.
5. إيقاف العملية وإنشاء عملية OS جديدة بنفس الإعدادات والجذر والـworkspace ID.
6. إعادة الطلب الموقع نفسه دون إصدار grant جديدة أو تغيير nonce أو audience: **ALLOW**، وملفا الجذر يصبحان النسخة المعتمدة مجددًا.

هذه حالة **ABA**: A = base المعتمدة، B = حالة ما بعد التطبيق، ثم الرجوع إلى A. وهي تعزل replay protection عن الحماية العرضية التي يوفرها اختلاف base بعد تطبيق ناجح.

**الحدود:**

- دون إعادة base قد يُرفض الطلب بسبب اختلاف hash، لا بسبب تذكر الاستهلاك. لذلك لا نقول إن كل replay بعد restart سينجح.
- لم تُدوَّر audience بعد restart. تدويرها إجراء تشغيلي مذكور سابقًا، لكنه ليس تخزينًا دائمًا لاستهلاك التفويض.
- سجل workspaces نفسه موجود في الذاكرة. أعاد fixture تسجيل **موقع workspace فقط** عبر المنفذ الحقيقي وبالمعرف نفسه، كي لا يُحسب رفض «workspace غير موجود» حماية replay. لم يُعد أو يُمسح replay/usage state يدويًا.
- هذا لا يثبت أن خادم HTTP يستعيد workspaces تلقائيًا بعد restart؛ إثبات استعادة التطبيق كاملة يحتاج عقد recovery مستقلًا.

ملخص diagnostics المقاسة:

```text
firstPid != restartedPid
sameProcess: DENY
afterRestart: ALLOW
a.txt: approved A
b.txt: approved B
```

## 4. H2 — عطل بعد نجاح الملف الأول

يُحمّل [مشغّل hardening](../tests/fixtures/celia-commit-hardening-child.mjs) نسخة الإنتاج دون تعديل، ويغلف `node:fs.writeFileSync` **داخل عملية الاختبار فقط**، مع `syncBuiltinESMExports` حتى تستخدم الوحدات الأصلية نقطة الاعتراض نفسها.

- الملفان موجودان في الجذر قبل التجربة: `a.txt` و`b.txt`.
- يجتاز الطلب التفويض والتحقق من البصمتين.
- كتابة A تُنفّذ بواسطة `writeFileSync` الأصلية وتنجح.
- عند محاولة كتابة B يُحقن خطأ `ENOSPC` مرة واحدة قبل كتابة B.
- يسمح الغلاف لأي عمليات تراجع لاحقة بالعمل؛ لا يحقن الفشل مجددًا ولا يمنع rollback.

الأثر المقاس:

```text
write-applied(a.txt)
fault(b.txt, ENOSPC)
result: ERROR
a.txt: approved A
b.txt: base B
```

معيار الاختبار بعد هذا الفشل: استعادة المحتوى وبنية الملفات الأصلية، وبقاء staging كما كانت. لا يفرض استعادة `ctime` المستحيلة بعد rollback عادي. لا يكفي إرجاع ERROR بينما بقي A مطبقًا.

**الحدود:** الاختبار يثبت تطبيقًا جزئيًا بعد خطأ I/O محقون. لا يختبر انقطاع الطاقة، أو قتل العملية وسط التطبيق، أو رؤية قارئ خارجي لحالة وسيطة، أو ضمانات `fsync` على قرص حقيقي ممتلئ. هذه ضمانات إضافية، لا PASS ضمني لها.

## 5. H3 — تعديل خارجي بعد التحقق، وليس قبل استدعاء COMMIT

نقطة التوقف هي استدعاء أول `writeFileSync` لملف الجذر، بعد أن أكمل التنفيذ الأصلي:

```text
signature/capability/policy
  → capture staging/base
  → compare hashes
  → consume authorization
  → [نقطة جدولة الاختبار]
  → actual target write
```

عند هذه النقطة يشغّل fixture [كاتبًا خارجيًا](../tests/fixtures/celia-commit-external-writer.mjs) باستخدام عملية OS مستقلة:

1. يقرأ الكاتب A ويتأكد التقرير أن قيمتها ما تزال base الأصلية.
2. يكتب `external writer value` إلى الملف الحقيقي، ويقرأها للتحقق.
3. ينتهي الكاتب، ثم يستأنف COMMIT الاستدعاء الأصلي للكتابة دون تبديل المحتوى أو البصمات أو نتيجة السياسة.

`spawnSync` هنا حاجز جدولة حتمي: عملية COMMIT موجودة ومتوقفة بينما الكاتب الخارجي يعمل. لا sleeps أو polling أو اعتماد على الحظ في ترتيب السباق. الكاتب مختلف PID عن عملية COMMIT وعن test runner.

الأثر المقاس:

```text
external process: A = external writer value
COMMIT: write-applied(A), write-applied(B)
result: ALLOW
final A = approved A       # تعديل الكاتب ضاع
final B = approved B
```

المطلوب في هذه التجربة: رفض الحالة القديمة، وبقاء A بقيمة الكاتب الخارجي وB بقيمتها الأصلية؛ لم يتحقق ذلك.

**الحدود:** هذا إثبات لحالة interleaving محددة للـcheck/use، وليس اختبار ضغط إحصائيًا. الكاتب لا يلتزم بقفل تعاوني. فحص hash إضافي قبل الكتابة فقط لا يزيل النافذة؛ تحديد ضمان التعامل مع كاتب خارجي يتطلب اختيار نموذج عزل/قفل/تطبيق مناسب، لا وعدًا بأن غياب `await` يمنعه.

## 6. سلامة أدوات الاختبار

- [fixture الأب](../tests/celia-commit-hardening-helpers.mjs) ينسخ `packages` و`adapters` و`tools` و`package.json` إلى مجلد مؤقت، دون `.git` أو الملفات المخفية أو `node_modules` أو الروابط الرمزية.
- لا توريث لأسرار التشغيل أو `NODE_OPTIONS`، ولا اتصال خارجي أو قاعدة بيانات.
- نقطة الاعتراض لا تعمل إلا أثناء COMMIT وبالملفين `a.txt` و`b.txt` في الجذر المؤقت. كتابة staging والتحقق والتوقيع والقراءات والبصمات ليست mocks.
- H1 يعيد تشغيل عملية حقيقية ويحافظ على القرص والإعدادات، دون إعادة توقيع الطلب.
- توجد مهل للأوامر والكاتب الخارجي والاختبارات، وتنظيف للعمليات والمجلدات حتى مع assertions فاشلة.
- آلية الحقن مرتبطة باستدعاء الكتابة الحالي. عند إعادة تصميم executor يجب نقل نقطة الحقن بما يحافظ على الدلالة؛ عدم وصول الاختبار إلى نقطة الحقن يفشل التهيئة ولا يُحسب PASS.

**حالة القبول:** عقد التفويض المحلي السابق ما يزال ناجحًا في اختباراته المحددة؛ hardening H1/H2/H3 ما يزال RED. لا merge أو deploy ولا ادعاء بجاهزية عامة.

## 8. قرار المرحلة التالية — دون تنفيذ إصلاح هنا

1. **H1:** تحديد سجل استهلاك دائم وحجز قبل الأثر، وربطه بالـaudience/grant/request، مع سياسة fail-closed عند تعذر التخزين أو وجود عملية غير محسومة بعد crash.
2. **H2:** تحديد معنى atomicity أولًا: عدم بقاء حالة جزئية بعد الفشل، أم عدم إظهارها لأي قارئ أثناء التطبيق أيضًا. ثم اختبار التعافي والـfailure points دون تسويق النسخ المتتابع كـtransaction.
3. **H3:** تحديد من يملك حق الكتابة خارج العملية وكيف يُفرض ذلك. الفصل بين كاتب متعاون مع الأقفال وكاتب قادر على تجاوزها أساسي قبل اختيار الحل.

هذه توصيات تصميم مبنية على RED وليست إصلاحات منفذة. تبقى create وSupabase خارج المرحلة، مع إبقاء RLS correctness وreal connector بوابتين منفصلتين.
